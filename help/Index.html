Sketchpad Architecture

This document provides two complementary views of Sketchpad architecture:

  • A high-level overview (“mental model”) for fast re-entry and orientation.
  • A detailed architectural map (“how it really works”) for implementation and debugging.

This is a raw help HTML file intended to be dropped directly into the Sketchpad help system.

Part 1 — High-Level Overview (Mental Model)

Sketchpad is not one monolithic application. It is a set of independent tab subsystems that share a common UI shell and a common drawing surface.

At the highest level, Sketchpad is built around five major “pillars”:

  1. Tab architecture (TabSpec lifecycle + uiState restoration)
  2. Content inventory (manifests + registry files + caching)
  3. Rendering (shared canvas + drawing lifecycle)
  4. UI composition (caption bar, categories grid, controls, overlays)
  5. Node service layer (maintenance + filesystem operations)

1. Tabs are independent subsystems

Each top-level tab (Draw, Patterns, Gallery, Utilities, Home, Figures, etc.) is its own subsystem. It owns its regions and its internal state.

Each tab is activated through a TabSpec that defines:

  • init() — cold start only
  • restore() — rebuild from saved uiState only
  • save() — snapshot current state before leaving the tab

The core principle is: UI state drives the UI, and is updated before rendering.

2. Manifests and registries define what content exists

Sketchpad content is discovered and organized by inventory sources:

  • Patterns: filesystem manifests under /patterns/<category>/manifest.json
  • Gallery: domain registries + per-category manifests under /gallery/<Domain>/
  • Home: a generated flat manifest under /home/manifest.json
  • Draw: internal registry objects (drawRegistry entries) loaded as modules

Manifests are loaded once, cached, treated as immutable, and only invalidated intentionally.

3. Drawing uses a consistent lifecycle

Whether a drawing is a drawRegistry entry or a Gallery/Patterns script, the mental model is the same:

  • params hold JSON-safe UI values
  • controls describe UI metadata
  • elements hold runtime drawing objects
  • init() creates elements once
  • update(params) copies values into elements
  • draw() renders deterministically from elements

The draw function reads from elements.element, not directly from params.

4. Node maintenance is separate from UI rendering

Maintenance tasks (rebuild manifests, archive items, edit manifest titles, generate thumbnails, etc.) are executed by a Node service layer.

Node tasks change files on disk and return structured results. The browser then invalidates caches and re-renders based on uiState.

Part 2 — Detailed Architecture (Subsystem Map)

This section is organized as a “map of responsibilities.” The goal is to make debugging deterministic: if something breaks, you should be able to identify which subsystem owns the failure.

A. Core UI Shell

A1. uiState.js (Authoritative UI state)

uiState is the authoritative record of what the user is currently viewing.

Each tab has a state container, typically with:

  • activeCategory
  • activeItem (or activeIndex)
  • activeSubtab
  • saved (the restore snapshot)

Architectural rule: uiState is updated immediately on user action, before any rendering occurs.

A2. setUI.js (Tab activation and lifecycle orchestration)

The UI shell owns tab switching and lifecycle dispatch.

The shell must:

  • switch themes
  • clear regions on cold init
  • call TabSpec.init(restoredFlag) OR TabSpec.restore()
  • call TabSpec.save() before leaving a tab

Architectural rule: setUI.js does not render content. It only delegates to the active tab subsystem.

B. Shared UI Components

B1. categories.js (Category grid renderer)

categories.js is a pure renderer. It does not know about manifests, tabs, or filesystem layout.

Input contract: an array of category frames where each frame contains:

  • frame title
  • items array
  • each item includes an onClick handler

Architectural rule: tabs build descriptor arrays; categories.js only renders them.

B2. caption.js (Caption bar + navigation + menu)

caption.js builds the caption bar for a tab view.

The caption bar is the single point where these concerns converge:

  • title display
  • Prev / Next navigation callbacks
  • menu anchor and dropdown invocation
  • optional click-zone overlay enabling/disabling

Architectural rule: caption behavior must be driven by the same callbacks used for navigation.

B3. ui_utilities.js (Shared mechanical helpers)

ui_utilities.js contains shared helpers for mechanical UI work.

Examples include:

  • thumbnail grid rendering
  • selected thumbnail highlighting
  • commands button wiring
  • offcanvas creation and display
  • small DOM utilities (clear regions, etc.)

Architectural rule: base controller functions should remain readable; helpers do mechanical DOM work.

B4. menuManager.js + menuCmds.js (Menu system)

The menu system provides a structured way to attach commands to the caption bar.

Typical flow:

  1. tab builds an info object (manifestPath, filename, matchField, etc.)
  2. tab calls get<Tab>CaptionMenuItems(info)
  3. menuManager.open(items, anchor)
  4. menuCmds executes commands (archive, edit, view source, etc.)

Architectural rule: per-tab menu command modules shape data; shared menuCmds does the work.

C. Drawing and Script Execution

C1. Shared canvas + ctx contract

Sketchpad assumes one shared coordinate space and one authoritative drawing context.

Core constraints:

  • There is exactly one canvas and one drawing context
  • Drawing code uses ctx directly
  • No script may create or resolve ctx
  • If ctx is missing, the system must crash loudly

This is required so overlays, nodes, handles, guides, and figures can interconnect.

C2. drawRegistry entries (internal objects)

A drawRegistry entry is an object placed on window with a predictable name, such as:

window.drawRegistry_mysticRose

Each entry describes one “first-class object” that can be selected, controlled, and drawn.

The entry contains:

  • metadata (name, id, category, tags, description, version)
  • style fields (background, overlays, transforms)
  • params (JSON-safe defaults)
  • controls (UI metadata)
  • elements (persistent runtime state)
  • init/update/draw lifecycle

Architectural rule: init() creates elements once, update() mutates elements, draw() renders deterministically.

C3. runPattern() (script entry point)

runPattern() is the entry point for executing a script module in Sketchpad.

The contract is:

  1. printTitle(scriptInfo.title)
  2. alias setup (scriptInfo.parameters = scriptInfo.params)
  3. init() called exactly once per load
  4. buildParameterControls(scriptInfo, targetId, true)
  5. explicit first draw (usually via redrawHandler)

Architectural rule: runPattern() orchestrates; it does not implement drawing math.

C4. scriptRunner.js (module loading and execution)

scriptRunner is responsible for:

  • importing ES modules by path
  • executing the expected entry point (runPattern or equivalent)
  • providing consistent error reporting paths

Architectural rule: loading and execution are separate from UI state and category selection.

D. File Inventory and Path Logic

D1. manifest.js (Loading + caching inventory)

manifest.js provides a centralized way to load and cache manifest data.

Key principles:

  • manifests are loaded once
  • cached data is treated as immutable
  • tabs read cached data only
  • cache invalidation is explicit (clearCache)

D2. fileLayer.js (File path normalization + identity)

fileLayer.js exists because Sketchpad must operate across multiple directory systems:

  • patterns: category folders
  • gallery: domains + categories
  • home: rooted paths pointing into other trees
  • utilities: scripts and logs

The role of fileLayer.js is to enforce consistent path rules and identity rules.

Typical responsibilities include:

  • normalizing relative paths
  • deriving canonical identifiers used for manifest matching
  • preventing category-prefix duplication (e.g. "3D/401.jpg")
  • providing stable keys for menu operations (archive/edit)

Architectural rule: if the manifest identity is wrong, maintenance commands will break. fileLayer.js is where those identity rules should live.

E. Node Service Layer (Maintenance and Generation)

The Node service layer exists to perform filesystem work that the browser cannot do.

Node tasks must be invoked explicitly through the dispatch service.

E1. nodeLayer.js (Browser → Node bridge)

nodeLayer.js is the client-side dispatcher.

It sends structured requests:

  • requestName
  • payload

And it receives structured results:

  • success/failure
  • report object
  • log name or log content

Architectural rule: nodeLayer does not interpret UI context; tabs shape payloads.

E2. sketchpadService.mjs (Central dispatch service)

sketchpadService.mjs is the Node-side service entry point.

It hosts the dispatch table and executes filesystem tasks.

Typical task categories:

  • manifest maintenance
  • archive item operations
  • thumbnail writing
  • manifest edits (title/status changes)
  • validation reports and log generation

Architectural rule: the service returns structured JSON; the browser decides how to display it.

E3. maintain_manifests.mjs (Inventory rebuild and validation)

maintain_manifests.mjs is a Node maintenance script responsible for generating and validating manifest data.

Its purpose is to keep the filesystem inventory consistent with the UI’s expectations.

It typically:

  • scans directories for categories and items
  • updates manifest.json files
  • generates reports of added/broken items
  • creates log output for inspection

Architectural rule: this script is authoritative for “what exists on disk.” Tabs must not guess inventory.

F. Tab Subsystems (Ownership Summary)

F1. Draw Tab

  • Inventory: drawRegistry entries
  • State: uiState.draw
  • Runtime: init/update/draw lifecycle on registry objects

F2. Patterns Tab

  • Inventory: /patterns/<category>/manifest.json
  • State: uiState.patterns
  • Runtime: imported modules + runPattern contract

F3. Gallery Tab

  • Inventory: /gallery/<Domain>/directoryRegistry.json + per-category manifests
  • State: uiState.gallery
  • Runtime: images OR imported scripts

F4. Utilities Tab

  • Inventory: utilities scripts and tools
  • State: uiState.utilities
  • Runtime: maintenance reports + script execution

F5. Home Tab

  • Inventory: /home/manifest.json (generated)
  • State: uiState.home
  • Runtime: scripts or images based on file extension

Summary

Sketchpad architecture is a deliberate separation of concerns:

  • Tabs are independent subsystems that own their regions and state.
  • Manifests and registries define inventory and are cached as immutable.
  • Drawing is standardized around init/update/draw and elements.element.
  • UI helpers render; controllers decide behavior.
  • Node services perform filesystem work; UI invalidates caches and restores from uiState.

This separation is what makes Sketchpad deterministic, fail-fast, and maintainable.
