menuManager.js — Caption Menu Manager and Help-Item Builder

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on one file:

  • ui/menuManager.js
Scope of this treatise
1) What menuManager is for (and what it is NOT for).
2) The life cycle: lazy init, open, close, outside-click dismissal, Escape dismissal.
3) How menu items are validated and rendered.
4) The special helper buildHelpItem(tabName, helpKey) and how it integrates with the help manifest.

1. What this file is in the Sketchpad architecture

menuManager.js provides a small, reusable “caption dropdown menu” system:

  • Build and show a menu (a floating DOM panel) anchored to a specific UI element.
  • Render a list of menu items (label + click handler), with optional disabled items.
  • Dismiss the menu deterministically on outside click or Escape.
  • Support a “Help” menu item that is enabled/disabled based on the help manifest.
Boundary rule
menuManager is a UI utility. It is NOT a tab controller.
It does not decide what commands a tab should have; it only displays the menu that a tab provides.

2. Core design: non-IIFE + lazy-init

This file is explicitly designed to be “lazy-init capable”. It has a module-level ready flag and requires an explicit initialization call: 

export function initMenuManager() {
  ready = true;
}

Any attempt to open a menu before initialization triggers a fail-fast error: 

menuManager: not initialized (call initMenuManager first)
Why this matters
In a modular UI, you often want a predictable startup sequence: initialize shared UI utilities first, then allow tabs to use them. The ready flag enforces that contract.

3. Public API surface

The module exports two things:

  • initMenuManager() (explicit one-time initialization)
  • menuManager object with methods: open, close, clear, createMenuItem, buildHelpItem, and isReady().

Everything else in the file is private helper functionality used to implement those exports.

4. Internal state (module-private)

The menu is managed as a single instance at a time. The file keeps these module-private variables:

  • menuEl — the DOM element for the currently open menu (or null)
  • outsideHandler — the document mousedown handler used to detect outside clicks
  • escHandler — the document keydown handler used to detect Escape
  • ready — whether initialization has occurred
Single-menu invariant
Calling open always closes any existing menu first. This guarantees only one menu exists in the DOM at a time.

5. Creating and validating menu items

5.1 createMenuItem(label, onClick, disabled=false)

createMenuItem is a convenience constructor that produces the standard item shape: 

{ label, onClick, disabled }

It enforces that label is a string (fail-fast).

Intent
Tabs can build menus using a consistent item format without duplicating object literal boilerplate.

5.2 validateItems(items)

Before rendering, the menu validates the item list:

  • items must be an array.
  • Each item must exist and have a label string.
  • If the item is NOT disabled, it must have an onClick function.
Fail-fast behavior
If a tab provides malformed items, open throws immediately, rather than silently rendering a broken menu.

This is consistent with your overall Sketchpad design preference: missing wiring should crash loudly so you can fix it.

6. Rendering and positioning: open(items, anchor)

open is the workhorse. It requires:

  • items — array of validated menu item objects
  • anchor — a real DOM element (HTMLElement) that the menu is positioned under

6.1 High-level open sequence (exact)

  1. Ensure ready (must call initMenuManager first).
  2. Validate items is an array and anchor is a DOM element.
  3. Validate item structure via validateItems.
  4. Close any existing menu (close()).
  5. Create menuEl (a <div> with class caption-menu).
  6. For each item, create a caption-menu-item div:
    • Set text to label.
    • If disabled, add disabled class and no click handler.
    • If enabled, attach click handler that closes then calls item.onClick().
  7. Append the menu to #wrapper.
  8. Position the menu under the anchor using positionMenu(anchor, menuEl).
  9. Install dismissal handlers:
    • Outside mousedown closes the menu.
    • Escape key closes the menu.
Why append to #wrapper?
It keeps menus inside your main UI container so they inherit positioning assumptions and theme styles. It also makes it easy to reason about z-index and overlay interactions.

6.2 positionMenu(anchor, menuEl)

The positioning strategy is simple and explicit:

  • Get the anchor’s viewport rect (getBoundingClientRect()).
  • Add scroll offsets (pageXOffset, pageYOffset).
  • Set absolute positioning so the menu appears directly under the anchor (with a 4px gap).
Implication
The menu is “document-positioned” (absolute in page coordinates). If you later change the layout so #wrapper becomes a positioned container with its own coordinate system, the positioning rules may need revisiting.

7. Closing behavior: close() and clear()

7.1 close()

close is responsible for cleanup:

  • Remove menuEl from the DOM if present.
  • Clear menuEl reference to null.
  • Remove outside-click handler if installed.
  • Remove Escape handler if installed.
No listener leaks
The close path always removes its document-level listeners, so menus do not accumulate handlers over time.

7.2 clear()

clear() is just an alias for close(). It exists because some callers prefer the semantic “clear menus” phrasing.

8. The special helper: buildHelpItem(tabName, helpKey)

buildHelpItem is an async factory that builds a single menu item:

  • If help exists for the current context, return an enabled “Help” item that opens the overlay.
  • If help does NOT exist, return a disabled “Help” item.
Key architectural point
Tabs can always include “Help” in their caption menu without duplicating existence checks. buildHelpItem centralizes the “is this help available?” decision.

8.1 How it decides if help exists

The help system is driven by a separate help manifest that lists which help pages exist. buildHelpItem loads that manifest via: 

const helpData = await loadHelpManifest();   // cached, deterministic

It then reads the list for the tab: 

const list = helpData[tabName];

If that is not an array, Help is disabled. If it is an array but does not include helpKey, Help is disabled.

Important detail
This uses the help manifest as the authority, not filesystem probing. That keeps the UI deterministic and avoids repeated HTTP probes.

8.2 The help path and overlay launch

If the help key exists, buildHelpItem constructs: 

/help/<tabName>/<helpKey>.html

and returns an enabled menu item that calls: 

showHelpOverlay(path, helpKey)

So:

  • menuManager decides whether “Help” is enabled.
  • overlay.js decides how help is displayed.
  • ui_utilities.js provides the cached help manifest loader.
Separation of concerns
This file does not render help content itself; it simply wires an action to open help.

9. What the imports imply (and what is currently unused)

The file imports:

  • showHelpOverlay from overlay.js
  • fileLayer from fileLayer.js
  • manifest from manifest.js
  • loadHelpManifest from ui_utilities.js
Current code reality
In the code you pasted, fileLayer and manifest are imported but not used. That is harmless at runtime but it is “noise” that can mislead a reader about dependencies.

Interpreting intent:

  • loadHelpManifest is the true authority for help existence.
  • fileLayer could be used for existence probing, but the manifest-driven model has replaced that need.
  • manifest appears unnecessary here unless later menu items depend on content manifests.

If you keep the imports, it implies “this module might later expand to include manifest-driven items beyond Help”. If you remove them, it clarifies the current boundary.

10. How tabs are expected to use menuManager

A typical pattern for a caption “menu” button is:

  1. Tab builds an array of items (some enabled, some disabled).
  2. Tab calls menuManager.open(items, anchorElement).
  3. The menu renders and manages its own dismissal and cleanup.

Items are usually created either as raw object literals or via: 

menuManager.createMenuItem("Label", handler, disabled)

For help, the tab can do: 

const helpItem = await menuManager.buildHelpItem(tabName, helpKey);

then include helpItem in the menu items list.

11. Summary checklist

  • menuManager shows one floating caption menu at a time.
  • Lazy init: initMenuManager() must be called before any open.
  • Fail-fast item validation catches missing labels and missing click handlers for enabled items.
  • Deterministic dismissal: outside click and Escape both close the menu and remove listeners.
  • buildHelpItem enables/disables Help based on the cached help manifest and opens help via showHelpOverlay.
  • Imports: in the current version, fileLayer and manifest are unused and may be removed for clarity.

End of treatise.
