parameterControls.js — Normalized Parameter Controls (Data First, DOM Second)

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on one file:

  • ui/parameterControls.js
Scope of this treatise
1) The core concept: controls are built as normalized data, then rendered into a tab’s Action area.
2) What “sourceInfo” must contain for Draw vs Scripts environments.
3) The rendering contract: writes only into #action and is a destructive rebuild.
4) A brief, practical description of each control widget (range, checkbox, select, color, point pickers, radio, button, staticText, hidden).

1. What this file is in the Sketchpad architecture

Sketchpad has a single, recurring requirement across multiple tabs: “Given a parameter schema and current values, show controls in the left Action panel, and when a control changes, update parameters and redraw.”

parameterControls.js is the shared implementation of that idea. It deliberately splits the problem into two phases:

  1. Build phase (data-only): Create a normalized control-data array describing controls in a uniform shape.
  2. Render phase (DOM): Use that normalized array to build DOM controls inside the current tab’s #action region.
Key architectural value
Tabs can share one renderer because the input is normalized: the renderer does not need to know whether the schema came from Draw registry entries or from scriptInfo objects.

2. The high-level entry point: buildParameterControls()

The public entry point is: 

buildParameterControls(sourceInfo, targetTabId = "tab-generic", render = true)

It selects an “environment” by inspecting targetTabId prefixes:

  • targetTabId starts with tab-scripts: controls are extracted from a script descriptor object (Scripts/Tools environment).
  • targetTabId starts with tab-draw: controls are extracted from Draw tab state (Draw environment).

It always returns the normalized control-data array, and optionally renders it immediately.

Why render is optional
Rendering can be skipped so callers can inspect the normalized array, test schemas, or reuse the same control definitions in another context.

3. Normalization: “control data” schema (the unified control descriptor)

Both builders (buildDrawParameterData and buildScriptParameterData) produce the same kind of array: 

[
  {
    key: "radius",
    label: "Radius",
    widget: "range",
    min: 0,
    max: 200,
    step: 1,
    options: null,
    value: 120,
    default: 100
  },
  ...
]

This is the normalized shape the renderer depends on. The meaning of the key fields is:

  • key: parameter identifier (the index into info.parameters[key]).
  • label: UI label text.
  • widget: which control renderer is used (range/checkbox/select/etc.).
  • min/max/step: numeric constraints (where relevant).
  • options: select/radio option list (where relevant).
  • value: the current value to display in the UI.
  • default: a reset baseline for future use (not always used directly).
Button control special case
Buttons do not have a normal “value”. They need in-memory action metadata. The normalization preserves action and optional redraw flags so the renderer can build a working button.

4. Draw environment: buildDrawParameterData(tabState)

The Draw builder expects a “tabState-like” object. In your comments, this is the Draw tab’s uiState slice. It uses:

  • tabState.drawRegistry as the schema source
  • tabState.parameters as the current value source

Schema selection rule:

  • Preferred: drawRegistry.controls
  • Fallback: drawRegistry.params

Value resolution rule:

  1. tabState.parameters[key] (current uiState value)
  2. def.default (schema default)
  3. empty string
Meaning
The Draw builder is the bridge from “registry entry schema + uiState current values” into the unified normalized control descriptor list.

5. Scripts environment: buildScriptParameterData(sourceInfo)

The Scripts builder expects a “script descriptor-like” object:

  • sourceInfo.controls (schema)
  • sourceInfo.parameters (current values)

It normalizes into the same control descriptor list, plus:

  • For widget === "button", it preserves: item.action and item.redraw.
Key architectural value
This makes a script “feel” like a drawRegistry entry from the control system’s point of view. Same widget vocabulary, same rendering pipeline, same handler shape.

6. Rendering contract: renderParameterControls()

The DOM renderer is: 

renderParameterControls(sourceInfo, controlData, targetTabId = "tab-generic")

It has one hard DOM dependency:

  • #action must exist (fail-fast if not).

It then performs a deterministic, destructive rebuild:

  1. Clear #action completely.
  2. Create #drawControls (historical id; means “parameter controls container”).
  3. If there are no controls, write (no parameters).
  4. For each normalized item, call buildSingleControl(...) to create a field.
  5. Skip null fields (hidden/suppressed controls).
Important boundary
This renderer does not create tab structure. It assumes the tab already built its shell. It only fills the Action panel for the active environment.

7. Event model: what a control does when it changes

Almost every interactive control follows the same runtime pattern:

  1. Update the parameter model: info.parameters[key] = newValue (or update x/y for points).
  2. If present, call info.onParamChange().
  3. Call info.redrawHandler().
  4. If def.rebuildControls is true, rebuild the Action panel controls from schema again.
Important nuance in your current code
Some control builders treat onParamChange as optional (scripts may omit it), while others are strict (some builders enforce it). This reflects mixed “fail-fast vs compatibility” decisions inside the file.

8. buildSingleControl(): widget dispatch table

buildSingleControl(info, key, def, value, tabId) is the widget switchboard. It does three key things:

  1. Suppress hidden controls (widget === "hidden") by returning null.
  2. Conditionally suppress staticText using def.showKey.
  3. Dispatch to the correct setXControl() builder based on def.widget.
Design intent
This is the single place where widget vocabulary is interpreted. Adding a new control type is primarily “add a new switch case + implement setNewControl()”.

9. Brief per-control descriptions (what each widget means)

These are the control types shown in the pasted file, with a brief “what it is / what it does” description.

9.1 hidden

  • Renders nothing (returns null so it does not consume space).
  • Used to keep a key conceptually in the schema without showing it in the Action panel.
  • In your current implementation, it does not mutate info.parameters; the caller/registry owns that.

9.2 range

  • Standard slider with a min/readout/max row.
  • On input: updates numeric value, updates readout, triggers redraw, optionally rebuilds controls.
  • Compatible with scripts that may not implement onParamChange.

9.3 rangeHeader

  • Alternate slider layout: header line “Label: value” with slider below; no min/max/readout row.
  • Designed to match a specific “reference UI” style.
  • More strict about required fields (explicit fail-fast checks in the function).

9.4 checkbox

  • Boolean toggle.
  • On change: stores true/false, triggers redraw, optional onParamChange.

9.5 select

  • Dropdown list driven by def.options.
  • Supports options as strings or objects { value, label }.
  • On change: stores the selected value; attempts to convert numeric strings back to numbers.

9.6 color / colorPicker

  • HTML color input (<input type="color">).
  • On input: stores hex string and triggers redraw.

9.7 text (default control)

  • Fallback input control when widget is unknown or explicitly “text”.
  • Uses def.type to choose input type (text/number/etc.).
  • On input: stores the new value; numbers are parsed as floats.

9.8 staticText

  • Display-only block of text; does not update parameters and does not redraw.
  • Text source: either def.text string or def.getText(info, key, def).
  • Can be conditionally hidden using def.showKey (suppressed by returning null).

9.9 button

  • Invokes an action rather than storing a value.
  • Action resolution supports: (A) def.action is a function, or (B) def.action is a string resolved via info.actions[def.action].
  • Optional def.redraw === true triggers redraw after the action.
  • Layout supports column-2 placement or full-row centering via def.fullRow.

9.10 radio

  • Mutually exclusive option group (exactly one selection).
  • Driven by def.options (strings or { value, label }).
  • On change: updates info.parameters[key], triggers redraw, optional control rebuild.

9.11 pointPicker

  • Controls a single point object {x, y} by dragging a dot on the interaction overlay layer.
  • Shows a read-only text readout (“x, y”) in the Action panel.
  • Dot is created under the canvas interaction overlay so it sits above the drawing.
  • On drag: updates x/y, calls onParamChange if present, triggers redraw.
  • Includes explicit dot cleanup logic to prevent duplicates on panel rebuild.

9.12 pointPickerArray

  • Controls an array of points by drawing N draggable dots on the interaction overlay layer.
  • Optionally suppresses readouts (dots-only mode) via def.noReadout.
  • Includes cleanup using a dot id prefix so dots do not accumulate across rebuilds for this key.
  • Uses a drag model similar to the single picker, but the pasted version installs some window listeners per dot.

10. How overlayManager participates

This file imports: 

import { overlayManager } from "./overlay.js";

The point pickers use the interaction overlay layer as the dot container:

  • overlayManager.canvasLayers["interaction"] is where dots are appended.
  • The dots are positioned absolutely, using pixel coordinates in the canvas coordinate system.
Conceptual fit
The Action panel shows control UI. The canvas overlay shows interactive handles. The two are connected by a shared parameters model and redraw handler.

11. Summary checklist

  • Two-phase design: build normalized control data first; render into DOM second.
  • Environment selection: Draw vs Scripts is selected by targetTabId prefix.
  • One rendering target: writes only into #action; destructive rebuild.
  • Unified widget vocabulary: range, checkbox, select, color, radio, button, staticText, hidden, point pickers.
  • Event loop: update parameters → optional onParamChange → redrawHandler → optional rebuildControls.
  • Overlay integration: point pickers draw draggable dots on the interaction overlay layer.

End of treatise.
