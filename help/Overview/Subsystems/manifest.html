The Manifest System: Loading, Caching, Invalidation, and Tab Registration

This treatise describes the current manifest architecture as implemented across ui/manifest.js, the tab lifecycle files, and ui/home/homeManifest.js. It supersedes the earlier treatise, which documented a simpler system without the registration/invalidation model.

Scope
1) The ManifestManager class: its four caches and six public methods.
2) How tabs register callbacks and how invalidation fires them.
3) How the standard tabs (Patterns, Gallery, Utilities, Figures) use the system.
4) How the Home tab differs and why.
5) The two global-reset operations that bypass the registration model.
6) How the Node service keeps /home/manifest.json consistent when items in other tabs are edited or archived.

1. ManifestManager: the four caches

ManifestManager is instantiated once as a singleton named manifest and imported by every file that needs manifest data. Its constructor initialises four dictionaries: 

this.cache        = {};  // basedir → raw loaded data (array or array-of-arrays)
this.registryCache = {}; // basedir → directoryRegistry array
this.shapedCache   = {}; // basedir → { categoryName: [entries] }  (lazily built)
this.listeners     = {}; // basedir → [ callback, ... ]

All four are keyed by basedir — the string passed to manifest.get(basedir). Examples of valid basedir strings: 

"patterns"
"gallery/Ideabook"
"gallery/Patterns"
"gallery/Scripts"
"utilities/Tools"
"utilities/Lab"
"figures"

Home is a special case and is discussed separately in section 5.

2. The six public methods

2.1 get(basedir)

The primary loader. Checks cache first; on a miss it loads from disk via fileLayer using one of two models:

  • DirectoryRegistry model — if /<basedir>/directoryRegistry.json exists, it is read as an array of category names. For each category, /<basedir>/<category>/manifest.json is loaded (or an empty array substituted if absent). The result is an array-of-arrays, one inner array per category. Both the result and the registry array are cached.
  • Flat model — if no registry exists but /<basedir>/manifest.json exists, it is loaded as a flat array and cached.
  • Nothing — returns and caches [].

All tabs call await manifest.get(basedir) during their init to prime the cache before calling getCategoryMap.

2.2 getCategoryMap(basedir)

Synchronous. Returns a plain object { categoryName: [entries], ... } shaped from the raw array-of-arrays. The shaped result is memoised in shapedCache and cleared automatically by both invalidate and clearCache. Throws if get(basedir) has not yet been awaited.

This is the method tabs use when they need to look up items by category name. It replaces the earlier pattern of tabs maintaining their own manifest.cache.patterns secondary cache.

2.3 register(key, callback)

Registers a zero-argument callback to be fired whenever invalidate(key) is called for that key. Multiple callbacks can be registered for the same key. Each tab registers once, guarded against duplicate registration on repeated inits: 

if (!initPatternsTab._registered) {
  manifest.register("patterns", () => restorePatternsTab());
  initPatternsTab._registered = true;
}

Registrations accumulate in listeners[key] and are never automatically cleared — they persist for the lifetime of the page. The duplicate guard on the _registered flag ensures each tab registers exactly once regardless of how many times its init function is called.

2.4 invalidate(key)

The primary mechanism for signalling that on-disk data has changed for a specific key. It does three things in order:

  1. Deletes cache[key], registryCache[key], and shapedCache[key].
  2. Logs the invalidation to the console.
  3. Fires every callback registered for that key.

The callbacks fire synchronously, so they execute before invalidate returns to its caller. Async callbacks (those that return a Promise) are not awaited — they run in parallel with whatever follows the invalidate call. This is intentional: the tab doing the edit does its own navigation independently, and background tabs refresh themselves without blocking the foreground work.

2.5 clearCache()

A global reset: wipes all three data caches (cache, registryCache, shapedCache) in one operation. It does not touch listeners — registrations survive a global reset. It does not fire any callbacks.

clearCache is reserved for two specific global-reset operations described in section 6. All other invalidation should use invalidate(key).

3. How the standard tabs use the system

Patterns, Gallery and Utilities all follow the same pattern. Figures registers a callback (below) but does not use manifest.get(): figuresDisplay.js fetches /figures/directoryRegistry.json and each category's manifest itself. getRegistry(basedir) returns the cached category list for a basedir (an empty array if none).

3.1 At init time

  1. Call await manifest.get(basedir) to prime the cache.
  2. Call manifest.getCategoryMap(basedir) to get the shaped data.
  3. Register a refresh callback (once, guarded by _registered).

3.2 After a Node operation that mutates a manifest

The tab's menu command calls manifest.invalidate(key). This clears the stale cache and fires the registered callback, which reloads and re-renders. The calling code then handles its own navigation (e.g. deciding whether to stay in pattern view or return to categories after an archive).

4. How Home differs

Home's manifest is architecturally distinct from all other tabs. The differences are not incidental — they follow from what Home actually represents.

4.1 What Home's manifest is

/home/manifest.json is a virtual aggregate: a flat array assembled by the Node rebuild service by scanning all status-bearing entries across every Patterns, Gallery, and Utilities manifest on disk. It is not the authoritative source for any item — the per-tab manifests are. Home's manifest is a derived view, rebuilt from scratch whenever rebuildAndValidateManifests runs.

4.2 Why Home bypasses manifest.get()

manifest.get("home") would first probe for /home/directoryRegistry.json, which does not exist. The dev server returns a 200 with an HTML error page rather than a 404 for unknown paths, causing fileLayer.exists() to return true and fileLayer.loadJSON() to fail on parsing.

Home's loader (loadHomeManifest_async in homeManifest.js) therefore bypasses manifest.get() entirely and calls fileLayer.loadJSON("/home/manifest.json") directly. It then stores the result manually into manifest.cache["home"] so that manifest.invalidate("home") can clear it in the normal way. 

// loadHomeManifest_async — simplified
if (Object.prototype.hasOwnProperty.call(manifest.cache, "home")) {
  data = manifest.cache["home"];          // cache hit
} else {
  data = await fileLayer.loadJSON("/home/manifest.json");  // disk read
  manifest.cache["home"] = data;          // store manually
}

4.3 Home's registration callback

Home registers a callback for "home" that only runs when Home is currently the active tab: 

manifest.register("home", () => {
  if (uiState.activeTab === "home") {
    loadHomeManifest_async();
  }
});

When another tab (e.g. Gallery) calls manifest.invalidate("home"), the cache is always cleared. If Home is active, the callback fires loadHomeManifest_async() immediately so the user sees the updated data without navigating away. If Home is in the background, the cache is already empty and the next time the user switches to Home it will load fresh data from disk.

4.4 Home's data shape

Unlike other tabs, Home does not use getCategoryMap. After loading, loadHomeManifest_async passes the flat array to groupHomeEntriesByStatus(data), which produces a plain object keyed by status string. Only entries that have a non-empty status field appear in this object — entries without a status exist in the flat array on disk but are invisible to Home's UI. 

{
  "working":  [ { file, path, title, status }, ... ],
  "favorite": [ ... ],
  "broken":   [ ... ]
}

This grouped object is stored in homeState via setHomeManifestGrouped() and drives Home's category frames.

5. Keeping Home consistent after per-tab edits

Because /home/manifest.json is a derived file, any edit to a per-tab manifest that adds, changes, or removes a status must also be mirrored into Home's manifest on disk. This is handled entirely in the Node service (node/sketchpadService.mjs) so the browser does not need to know about it.

5.1 editManifestEntry (Case A: editing from within a tab)

When the service writes a status change to a Patterns, Gallery, or Utilities manifest, it immediately mirrors that change into /home/manifest.json handling three cases:

  • Status newly set — the item does not yet exist in Home's manifest. A new entry is appended.
  • Status changed — the item already exists in Home's manifest. Its status and title are updated in place.
  • Status cleared — the item exists in Home's manifest. It is removed.

The match is made by rooted path — the item's absolute path from the project root, e.g. /gallery/Scripts/Arcs/arcsAndInner.js. This is computed by the makeRootedPath helper from the item's manifest directory and its local entry.path value. The response includes a homeMirrorResult field ("added", "updated", "removed", or "skipped") for diagnostics.

5.2 editManifestEntry (Case B: editing from within Home)

When the UI sends a manifest edit with manifestPath pointing to /home/manifest.json, the service treats this as a virtual edit. It uses the rooted path (the matchValue) to locate the original per-tab manifest entry, updates that file, and then also updates /home/manifest.json directly.

5.3 archiveItem

When an item is archived from any tab, the service removes it from the item's own manifest and also removes the matching entry from /home/manifest.json, again matched by rooted path. Both writes happen before the service returns, so the browser's subsequent manifest.invalidate("home") always finds correct data on disk.

6. Global reset operations

Two operations wipe the entire cache rather than invalidating specific keys. Both are in uiUtilities.js and are only called after the Node rebuild service has rewritten all manifests on disk.

  • syncSystemStateAfterRebuild() — clears the cache and marks all tab needsUpdate flags so each tab re-initialises on next visit.
  • rebuildAllSystemCaches() — clears the cache then immediately re-fetches all known basedirs in parallel to warm the cache proactively.

Neither fires registered callbacks — that is intentional. A global rebuild replaces all data from scratch and the tab lifecycle (via needsUpdate) handles re-rendering. Firing all callbacks would cause redundant re-renders before the fresh data arrives.

clearCache() should not be called outside of these two functions. All other invalidation uses invalidate(key).

7. End-to-end example: editing a Gallery/Scripts status

  1. User opens a Gallery/Scripts item, chooses Edit Manifest, sets status to "working", confirms.
  2. UI calls openEditManifestDialog() which dispatches editManifestEntry to the Node service.
  3. Node writes the new status to the item's manifest file, then mirrors it into /home/manifest.json (adding a new entry because none existed). Returns homeMirrorResult: "added".
  4. UI calls refreshGalleryFromManifestEdit(), which calls:
    • manifest.invalidate("gallery/Ideabook")
    • manifest.invalidate("gallery/Patterns")
    • manifest.invalidate("gallery/Scripts") — fires restoreGalleryTab()
    • manifest.invalidate("home") — fires Home's callback
  5. Home's callback checks uiState.activeTab:
    • If Gallery is active: cache is cleared, Home loads fresh on next visit.
    • If Home is active: loadHomeManifest_async() runs immediately, reads the updated file, re-groups by status, and re-renders.

8. Summary: what each layer owns

LayerResponsibility
manifest.js Loading, caching, shaped access, registration, and targeted invalidation. Knows nothing about tabs or UI.
Tab init functions Call manifest.get() to prime the cache, then register a refresh callback once.
Tab menu command functions Call manifest.invalidate(key) after Node operations, including "home" for any status-affecting operation. Handle their own navigation independently of the callback.
homeManifest.js Loads Home's flat manifest directly via fileLayer, stores into manifest.cache["home"] manually, groups by status, and updates Home's display state.
node/sketchpadService.mjs Writes per-tab manifests and mirrors every status change into /home/manifest.json immediately, so the browser never reads stale home data after a cache clear.
uiUtilities.js Owns the two global-reset operations (clearCache()) that follow a full Node rebuild. These do not fire callbacks.
