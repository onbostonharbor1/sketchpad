uiState Overview and How Tab Swapping Works

This document explains what uiState is, how it is structured, and how it is used during tab switching in the TabSpec architecture (cold init vs restore). It is written to be used as help-system reference material.

1. What uiState is (and what it is NOT)

uiState is one object that holds the entire “remembered UI situation” of the app. It is deliberately “pure data only.”

1.1 What it stores

  • Which tab is active.
  • What a tab was showing the last time you were there (view modes, selection, index).
  • Which category/item/domain/subtab is active within a tab.
  • Cached manifest pointers and manifest storage locations.
  • Overlay flags describing whether an overlay is active and what it is.

1.2 What it does NOT store

  • No functions.
  • No DOM nodes.
  • No “builders” or layout logic.
  • No behavior.

In other words: uiState is not “the program.” It is the program’s memory of where the UI is.

If you restart the app, uiState resets to defaults. If you switch tabs, uiState is rewritten so each tab can restore its own view later.

2. The main partitions inside uiState

uiState contains five main “domains” of data:

2.1 Transient intent (launch)

uiState.launch is a one-shot instruction: “after you land on some tab, immediately jump to another tab with context.”

  • pending is true when the intent must be consumed.
  • After consumption, pending must be set back to false.
  • This is transient state. It is not a tab’s saved restore contract.

2.2 Global configuration

  • canvasWidth, canvasHeight
  • activeTab

2.3 Per-tab state containers

Each tab has its own state bucket (home, draw, patterns, gallery, figures, utilities). Each bucket holds the tab’s current selections and (importantly) the tab’s saved restore contract.

2.4 Manifest cache storage

uiState.manifests provides places to store loaded manifest data (typically loaded once, cached, immutable).

2.5 Overlay state

uiState.overlay tracks whether an overlay is active and what kind it is. This is global, not per-tab.

3. The key concept: “saved” vs “active”

This is what usually makes uiState feel hard at first. Per-tab state has two categories of fields:

3.1 Active members (what is happening right now)

These represent current selections. Examples:

  • uiState.gallery.activeDomain
  • uiState.gallery.activeCategory
  • uiState.gallery.activeItem
  • uiState.patterns.activeCategory
  • uiState.activeTab (global)

3.2 Saved restore contract (how to rebuild after leaving and returning)

Each tab’s saved field controls cold init vs restore. 

saved == null   → “cold start required”
saved != null   → “restore required”

This is the central rule enforced by setUI.js: 

if uiState[tab].saved exists:
  call TabSpec.restore()
else:
  clearDivs()
  call TabSpec.init(false)

Practical meaning: saved is not “selection.” It is “the restore recipe.” If a tab forgets to update its saved contract during navigation, restore becomes wrong.

4. Tab swapping walkthrough (extended)

This section describes the end-to-end path used by your TabSpec orchestrator (ui/setUI.js).

4.1 What triggers a tab swap

  • User clicks a button under #mainTabs.
  • DOMContentLoaded wires each button to call handleTabChange(btn.id).
  • handleTabChange maps the HTML id to a tab key using mapTabIdToKey.
  • It calls setUI(tabKey).

The important architectural point: the only public entry for switching tabs is setUI(tab).

4.2 What setUI does first: theme

setUI applies theme before init/restore: 

applyTheme(tabName)
activateTab(tabName)

Theme-first matters because init/restore may build DOM that depends on the wrapper theme class.

4.3 What setUI does second: activateTab (restore vs cold init)

activateTab decides whether to restore or cold-init by checking uiState[tabKey].saved.

Case A: START

  • START always lands on Home.
  • It uses cold init: clearDivs() then HomeTabSpec.init(false).

Case B: normal tab

const saved = uiState[tabKey] && uiState[tabKey].saved;

if (saved) {
  restoreTab(tabKey);   // NO clearing
} else {
  initTab(tabKey);      // clearDivs() + init(false)
}

Then common fall-through: 

uiState.activeTab = tabKey;
setActiveTab(tabKey);   // cosmetic highlight

4.4 Who writes what in uiState during tab swaps

A) Orchestrator responsibility

  • Writes uiState.activeTab.
  • Consumes uiState.launch if pending.
  • Does not invent per-tab restore data.

B) Tab subsystem responsibility

  • Writes its own uiState.<tab>.saved restore contract.
  • Writes its own active fields (category/item/view/index/domain/subtab).
  • Decides what minimal fields are required to restore deterministically.

The orchestrator does not decide what a tab must remember. The tab decides what it needs to restore itself, and stores that in saved.

4.5 What “saved” must contain (the practical rule)

The restore contract must contain exactly enough information for TabSpec.restore() to rebuild the view deterministically. No more, no less.

Example: Gallery default restore template (conceptually): 

view: "categories" | "results"
domain: "Ideabook" | "Patterns" | "Scripts"
category: string | null
index: number | null

That is enough for restore to re-enter either:

  • categories view for a domain, or
  • results view at a particular index

5. How launch intent fits into tab swapping

uiState.launch is your controlled “second jump.” After a tab activates (init/restore), setUI checks for pending launch intent. 

if (!uiState.launch) return;
if (uiState.launch.pending !== true) return;

const targetTab = uiState.launch.targetTab;
if (!targetTab) throw ...

uiState.launch.pending = false;      // cleared FIRST
if (uiState.activeTab === targetTab) return;

setUI(targetTab);                    // jump

Subtle implication: the “first” tab still runs its init/restore normally before the jump occurs, because the launch check happens after activation. This is usually fine, but it’s good to be aware of it.

6. A clean mental model: the “three layers”

When reading uiState, it helps to treat it as three layers:

Layer 1: Orchestrator-global

  • activeTab
  • launch

Layer 2: Per-tab UI position (current selections)

  • activeCategory, activeItem, activeDomain, activeSubtab, etc.

Layer 3: Per-tab restore contract

  • saved (null vs object)

Then separately:

  • manifest caches (uiState.manifests)
  • overlay state (uiState.overlay)

If you keep these layers separate, uiState stops feeling “random” and becomes predictable.

7. Suggested discussion workflow (activities that use uiState)

You asked for “overview first, then discussions of the kinds of activities that use it.” Here is a clean order, because each activity exercises different parts of uiState:

A) Tab swapping (this document)

  • Focus: activeTab + the saved null/exists rule.

B) In-tab navigation (one tab at a time)

  • Focus: which active fields change on each navigation action.
  • Focus: how and when each tab rewrites its saved contract.
  • Example (Gallery): categories → results sets domain/category/index; prev/next updates index.

C) Cross-tab jump (launch intent)

  • Focus: who sets launch, who consumes it, and what fields are required (targetTab, registryKey, etc.).

D) Overlay usage

  • Focus: overlays are global; they should be cleared on tab change.
  • Focus: tab subsystems should not store overlay DOM; only state flags.
