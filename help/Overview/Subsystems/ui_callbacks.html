```html Help Treatise — ui_callbacks.js (Central UI Callback Layer)

ui_callbacks.js — Central UI Callback Layer (Third / Correct Version)

This file is (or was) a deliberate “routing hub” for UI events: it receives generic events (tab activated, category selected, item selected, etc.) and forwards them to the correct tab subsystem (draw/patterns/gallery/figures/utilities).

Important historical note
This file represents an earlier architecture than your current TabSpec-based setUI.js model. In this version, tab activation triggers direct calls like draw.initDrawTab(). In your current architecture, setUI.js delegates to TabSpec.init/restore. So: treat this as “explanatory legacy,” unless you are intentionally still using it.

1. What this file claims to be

The header comment says it is the “Third / Correct Version” and that:

  • No orchestrators
  • No generic tab APIs
  • Each tab uses its own functions
  • Only event routing lives here

That means the callbacks here should be “thin”: they should not contain domain logic, only dispatch logic.

2. Imports: who is involved

2.1 Shared state and overlays

  • uiState — global UI state
  • overlayManager — overlay system

2.2 Tab subsystems

Each tab subsystem is imported as a namespace:

  • import * as draw from "./draw.js"
  • import * as patterns from "./patterns.js"
  • import * as gallery from "./gallery.js"
  • import * as figures from "./figures.js"
  • import * as utility from "./utilities.js"
In this architecture, the callback layer assumes each tab module exposes specific entry points (init/load/save/show/prev/next/etc.). If those functions don’t exist, the system breaks immediately.

3. Callback: onTabActivated(tabName)

This function is the tab “activation router.” It does two shared actions first:

  1. uiState.activeTab = tabName
  2. overlayManager.clearAll() (clear panel overlays)

Then it dispatches to the tab-specific init:

  • draw → draw.initDrawTab()
  • patterns → patterns.initPatternsTab()
  • gallery → gallery.initGalleryTab()
  • figures → figures.initFiguresTab()
  • utilities → utility.initUtilityTab()

Any unknown tab throws: onTabActivated: unknown tab ...

Design implication
This callback layer is performing orchestration (init calls) even though the header says “no orchestrators.” It’s “thin orchestration,” but it is orchestration.

4. Callback: onCategorySelected(tabName, categoryName)

Common step: 

uiState[tabName].activeCategory = categoryName;

Then per-tab dispatch:

  • draw → draw.setDrawCategories()
  • patterns → patterns.loadCategory(categoryName)
  • gallery → gallery.loadCategory(categoryName)
  • utilities → utility.loadCategory(categoryName)
Draw is different: it ignores categoryName and calls a function that presumably reads uiState to decide what to show. Patterns/Gallery/Utilities directly load the selected category by name.

5. Callback: onItemSelected(tabName, itemName)

Common step: 

uiState[tabName].activeItem = itemName;

Then per-tab dispatch:

5.1 Draw

Draw does something special: it tries to locate a drawRegistry entry by matching e.name. 

const reg = window.drawRegistry || {};
const entry = Object.values(reg).find((e) => e.name === itemName);
if (!entry) throw new Error("draw item not found: " + itemName);

draw.addDrawSubtab({ name: entry.name, entry: entry });
This is a strong coupling point
The callback layer assumes drawRegistry is globally available on window, and that entries have a name property.

5.2 Patterns

  • patterns.loadItem(itemName)

5.3 Gallery

  • gallery.showImage(itemName)

5.4 Utilities

  • utility.runUtilityItem(itemName)

6. Callback: onParamChanged(paramName, newValue) — Draw only

This callback updates parameters inside the active draw subtab and redraws: 

const tabId = uiState.activeDrawTab;
const tab = uiState.drawTabs[tabId];
if (!tab) return;

tab.parameters[paramName] = newValue;
draw.drawActiveTab();
This uses silent returns instead of fail-fast errors: if (!tab) return; That is inconsistent with your later “crash immediately” style.

7. Help

This callback is very simple: 

overlayManager.show("help", html);

It assumes the “help” overlay layer exists and is registered.

8. Overlay operations (interaction layer)

These two functions call overlayManager against the “interaction” layer:

  • onOpenOverlay(html) → overlayManager.show("interaction", html)
  • onCloseOverlay() → overlayManager.hide("interaction")
Potential mismatch with your current overlay system
In your later overlay.js, “interaction” is a canvas overlay registered via registerCanvas, not a panel overlay in layers. overlayManager.show/hide currently operates on panel layers only. So if you run this against the newer overlayManager implementation, it will likely throw.

9. Navigation: prev/next (Gallery only)

Prev/Next are implemented only for Gallery here:

  • prev → gallery.showPrevImage()
  • next → gallery.showNextImage()

Other tabs emit console.warn.

10. Save routing

Save is routed per tab:

  • draw → draw.saveDrawState()
  • patterns → patterns.savePatternsState()
  • gallery → gallery.saveGalleryState()
  • utilities → utility.saveUtilityState()

Unknown tabs warn.

11. Reset parameters (Draw only)

Reset is implemented by re-running the registry init and replacing parameters: 

const tabId = uiState.activeDrawTab;
const info = uiState.drawTabs[tabId];
if (!info || info.type !== "object") return;

info.drawRegistry.init();
info.parameters = info.drawRegistry.params;
draw.drawActiveTab();
This assumes: 1) drawRegistry.init() is idempotent and safe to call at reset time 2) drawRegistry.params is the authoritative default parameters object

12. Export surface

At the end, all callbacks are exported as one object: 

export const callbacks = {
  onTabActivated,
  onCategorySelected,
  onItemSelected,
  onParamChanged,
  onHelpRequested,
  onOpenOverlay,
  onCloseOverlay,
  onPrev,
  onNext,
  onSave,
  onResetParameters,
};

This suggests other code calls callbacks.* rather than importing each function.

13. The real “meaning” of this file

Conceptually, ui_callbacks.js tries to be a single place where “UI events become tab actions.” The advantage is: you can find routing in one file. The disadvantage is: it becomes a second orchestrator layer that can drift out of sync with the tab modules and with your overlay system.

Compatibility warning with TabSpec architecture
If you are now using setUI.js and TabSpec.init/restore, then: - onTabActivated() duplicates orchestration logic - draw.initDrawTab() etc. will not match your current module entry points - overlay routing for “interaction” likely conflicts with the newer overlay.js In short: this file should either be retired, or rewritten to route into TabSpec.activate paths.

End of treatise.
```
