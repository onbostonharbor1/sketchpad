scriptRunner.js — Universal Script Loader and Deterministic Execution Pipeline

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on one file:

  • ui/scriptRunner.js
Scope of this treatise
1) What this module is responsible for (and what it refuses to do).
2) The script execution contract (which exports a runnable script must provide).
3) Why loadScriptModule() probe-fetches before dynamic import (the “Vite returns index.html” problem).
4) The two execution routes: canvas output vs text output.
5) Exactly what is reset when a script runs (and what is not).

1. What this file is in the Sketchpad architecture

Sketchpad has multiple places where a user can “run a script”: Patterns items, Gallery Scripts items, Utilities Lab, and Utilities Tools. These scripts come from different tabs and different directory trees, but the core runtime requirement is always the same:

Load an ES module by path, verify it is really a JavaScript module, then execute it in a deterministic and tab-appropriate way.

ui/scriptRunner.js is the single shared execution pipeline. Tabs are responsible for selecting the script path and deciding where it belongs. This module is responsible for:

  • Loading ES modules by rooted path
  • Fail-fast validation (missing file, wrong MIME type, missing exports)
  • Executing the script into either the shared canvas or the #text region
  • Resetting drawing state when (and only when) a canvas execution occurs
What it deliberately does NOT do
It does not interpret “meaning” of scripts, does not manage uiState, and does not decide which scripts exist or where they come from. That selection belongs to each tab/controller.

2. The execution contract (what scripts must export)

This module enforces a simple contract:

  • Preferred modern export: runPattern()
  • Legacy drawing export: drawPattern(params) (optionally with initPattern())
  • Text-only utilities: render()

In the current implementation, loadScriptModule() requires runPattern() to exist (fail-fast). The execution functions also include fallback logic for legacy patterns, but module loading itself is strict.

Practical interpretation
Treat runPattern() as the universal “entry point”. If a script is runnable in Sketchpad, it should export runPattern().

3. loadScriptModule(path): reliable module loading

loadScriptModule(path) accepts a rooted browser path such as: 

"/patterns/curve_stitch/parabola.js"

It performs five responsibilities in strict sequence:

  1. Validate input (must be a non-empty string).
  2. Normalize to rooted URL (ensure it begins with “/” and remove accidental “//”).
  3. Cache-bust in dev by appending a query string timestamp.
  4. Probe-fetch the URL with fetch():
    • Verify HTTP success (res.ok)
    • Verify JavaScript MIME type (content-type contains “javascript” or “ecmascript”)
  5. Dynamic import the module using the same URL (import(/* @vite-ignore */ spec)).

3.1 Why probe-fetch exists (the Vite fallback problem)

Vite (and many dev servers) will return index.html when a path is wrong. That produces confusing dynamic-import errors because the browser thinks it is importing JavaScript but receives HTML (text/html) instead.

Probe-fetch converts that into a fail-fast error with context:

  • It checks content-type before importing.
  • If it is not JS, it reads a short HTML snippet and includes it in the error.
Bottom line
Probe-fetch is the only reliable browser-side “does this module path actually exist” check in the presence of dev-server HTML fallbacks.

3.2 Contract enforcement at load time

After import, loadScriptModule() requires: 

typeof mod.runPattern === "function"

If not present, loading fails immediately. This ensures every runnable script has a single, predictable entry point for Sketchpad.

4. executeScriptToCanvas(mod, title): controlled canvas execution

executeScriptToCanvas(mod, title) runs a loaded module into the shared canvas. It enforces a deterministic canvas environment:

  1. Locate #sketchpad (fail-fast if missing).
  2. Clear it (pad.innerHTML = "").
  3. Reattach the shared canvas (pad.appendChild(window.drawCanvas)).
  4. Reset drawing state once, deterministically (resetCanvas()).
  5. Execute the script once (prefer runPattern()).
What “reset once” means
Sketchpad expects runPattern() to do as many drawing calls as it wants. This helper’s role is only to clear and reset the environment one time per script run, not to interfere with internal script sequencing.

4.1 Legacy fallback path

If a module does not use runPattern() but does provide legacy exports, this function supports:

  • initPattern() to provide params (optional)
  • drawPattern(params) to perform drawing

If neither runPattern nor drawPattern exists, it throws.

5. executeScriptToText(mod, title): controlled text/HTML execution

executeScriptToText(mod, title) is used for scripts that produce output intended for the #text region (Utilities → Tools).

It is explicitly non-canvas:

  • Does not touch #sketchpad
  • Does not attach a canvas
  • Does not call resetCanvas()

It clears #text, then executes:

  • Preferred: runPattern() and use its returned string as HTML if provided
  • Alternate: render() and use its returned string as HTML if provided

If no HTML is returned, it writes a small status message to #text and (in the “no usable output” case) throws an error.

6. Reset dependency: drawState.js and resetCanvas()

Canvas execution depends on a concrete import: 

import { resetCanvas } from "/draw/drawState.js";

This is intentionally a rooted “.js” import so that the browser never falls back to index.html. The reset step is what makes repeated executions deterministic: each run starts from a clean draw-state baseline.

7. How tabs should use this module (end-to-end pattern)

The expected tab/controller usage pattern is:

  1. Build a rooted script path (based on the tab’s manifest selection).
  2. const mod = await loadScriptModule(path);
  3. Choose output route:
    • executeScriptToCanvas(mod, title) for Patterns/Gallery/Lab
    • executeScriptToText(mod, title) for Tools
Division of responsibilities
Tabs decide which script to run and where its output should go. scriptRunner decides how to load it safely and execute it deterministically.

8. Summary checklist

  • Single pipeline: all runnable scripts are loaded and executed through this module.
  • Fail-fast loading: probe-fetch validates HTTP and MIME type before import().
  • Contract enforcement: modules must export runPattern().
  • Two execution targets: canvas (clears #sketchpad, reattaches canvas, calls resetCanvas()) vs text (writes HTML into #text, does not touch canvas).
  • Determinism: reset happens once per canvas execution, not per draw call inside the script.

End of treatise.
