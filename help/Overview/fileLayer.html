fileLayer.js — Unified File/URL/Path Abstraction (All Tabs)

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on one file:

  • ui/fileLayer.js
Scope of this treatise
1) What fileLayer is for, and what it is NOT for.
2) The “low-level ops” API: exists, loadText, loadJSON, listDirectory.
3) The “path helpers” API: fileLayer.path.* (the preferred way to construct paths).
4) The “legacy normalizers” and how to migrate away from them safely.

1. What fileLayer is in this architecture

fileLayer is a single place to put:

  • Minimal fetch-based I/O primitives for the browser runtime (read-only, via HTTP).
  • Consistent path construction so every tab builds the same URLs the same way.
  • Backward compatibility shims (“normalizers”) so older code keeps working while you migrate.
Strict boundary rule
fileLayer.js contains NO tab logic, NO UI logic, and NO manifest logic.
It does not know what a “Patterns item” is, what a “Gallery view” is, or what your UI state contains.

If you want a simple mental label:

  • fileLayer = mechanics (fetch things, build consistent paths)
  • tabs/controllers = meaning (how those paths and loaded data are used)

2. Why this file exists

Sketchpad spans multiple content roots and multiple “consumers” of files:

  • Manifest loading (manifest.js)
  • Help-page lookup (menu/help code)
  • Script/module loading (scriptRunner, Patterns/Gallery/Home/Utilities controllers)
  • Occasional directory listing hacks during development

Without a shared layer, each area tends to re-invent:

  • How to check if a file exists
  • How to fetch text vs JSON
  • How to normalize “item names” (strip or add “.js”)
  • How to build relative paths (the ../ vs / problem)
Common failure mode
Different tabs build slightly different paths to the same resource, so one works and another breaks.
fileLayer.path.* exists to eliminate that drift.

3. Low-level ops API (fetch primitives)

These methods do the smallest useful unit of work and return values that are easy for higher layers to interpret. They all operate on a path string that is expected to be a valid URL from the browser’s point of view.

3.1 exists(path)

exists(path) checks whether a resource is reachable by doing an HTTP HEAD request. If the server responds successfully (resp.ok), it returns true, otherwise false. 

const ok = await fileLayer.exists("../patterns/curve_stitch/manifest.json");
Design intent
exists is used as a “probe” before doing a heavier load, especially when optional files may or may not exist.
Important behavioral detail
On network or fetch errors, exists logs to the console and returns false.
That means a transport failure is indistinguishable from “does not exist” at the return-value level.

3.2 loadText(path)

loadText fetches a URL with GET and returns the response body as a string. If the HTTP response is not OK, or if fetch throws, it returns null. 

const src = await fileLayer.loadText("../patterns/curve_stitch/parabola.js");
Who uses it
“Show Script” features (offcanvas viewer) and any “read a file as text” logic.

3.3 loadJSON(path)

loadJSON is the JSON twin of loadText. It fetches with GET, and if the response is OK it returns await resp.json(). On HTTP failure or fetch/parse errors, it returns null. 

const items = await fileLayer.loadJSON("../patterns/curve_stitch/manifest.json");
Who uses it
Manifest loading code (directly or indirectly via manifest.js).

3.4 listDirectory(path)

listDirectory is a browser-only hack: it loads the HTML directory listing page and parses out href="..." attributes, returning a simple array of filenames. 

const names = await fileLayer.listDirectory("../patterns/curve_stitch/");
Critical limitation
This only works if your dev server exposes directory listings as HTML. Many servers do NOT, and in production you usually do NOT want this enabled.
Architecture note
This function is intentionally “low credibility” compared to manifests and Node scans. It is useful for development experiments, but manifests remain the authoritative content index.

4. Help existence convenience: helpExists(tabName, itemName)

helpExists(tabName, itemName) is a small convenience wrapper that constructs: 

/help/<tabName>/<itemName>.html

Then it calls exists(path). 

const hasHelp = await fileLayer.helpExists("patterns", "curve_stitch/parabola");
Key point
This is still “path + existence check”, not UI logic. It does not open overlays or render help.

5. Path helpers (NEW, preferred API)

The most important long-term purpose of fileLayer is standardizing path construction. This is done by a nested object: 

fileLayer.path.*

The goal is simple: higher-level modules should never hand-build these strings anymore. Instead they call a helper, so the rules are centralized and consistent.

Design rule
All higher-level modules (manifest, tabs, help, scripts) should construct paths only via fileLayer.path.* once migration is complete.

5.1 Manifest-related path helpers

These exist specifically so manifest.js can implement both directory models without hardcoding strings:

  • path.directoryRegistry(basedir) → ../<basedir>/directoryRegistry.json
  • path.categoryManifest(basedir, category) → ../<basedir>/<category>/manifest.json
  • path.flatManifest(basedir) → ../<basedir>/manifest.json
const regPath  = fileLayer.path.directoryRegistry("patterns");
const manPath  = fileLayer.path.categoryManifest("patterns", "curve_stitch");
const flatPath = fileLayer.path.flatManifest("home");
Why the leading "../"?
These helpers reflect that the UI code lives under /ui and must fetch sibling roots like /patterns, /gallery, /utilities.

5.2 Help path helper

  • path.helpHtml(tabName, itemName) → /help/<tabName>/<itemName>.html
const p = fileLayer.path.helpHtml("patterns", "curve_stitch/parabola");
Intentional difference
Help is rooted at /help (an absolute path), unlike content roots that are reached with ../.

5.3 Script path helpers

These helpers exist to unify how module paths are built and how “.js” suffixes are handled. Each helper strips a trailing .js if present, then adds it back in the returned URL.

  • path.script(tabName, itemName) → ../<tabName>/<itemName>.js
  • path.patternScript(category, file) → ../patterns/<category>/<file>.js
  • path.galleryScript(file) → ../gallery/Scripts/<file>.js
  • path.utilityScript(category, file) → ../utilities/<category>/<file>.js
// Generic "tab-rooted" script:
const a = fileLayer.path.script("utilities", "reconcileManifestWithFolder");

// Pattern category script:
const b = fileLayer.path.patternScript("curve_stitch", "parabola");

// Gallery script (Scripts subarea):
const c = fileLayer.path.galleryScript("spiral");

// Utility script within a category:
const d = fileLayer.path.utilityScript("maintenance", "validateManifests");
Path helper assumption
These helpers encode your current on-disk structure (for example: ../gallery/Scripts/).
If the folder layout changes later, you update it in ONE place.

6. Legacy normalizers (backward compatibility)

The bottom of the file contains “legacy normalizers”:

  • normalizeHelpPath
  • normalizeScriptPath
  • normalizePatternPath
  • normalizeGalleryScript
  • normalizeUtilityPath

Each one simply delegates to the corresponding fileLayer.path.* helper. They exist so older call sites can keep using the old names while new code uses the new API.

Migration strategy
Step 1: Keep normalizers so nothing breaks.
Step 2: Migrate call sites to fileLayer.path.* one subsystem at a time.
Step 3: When all call sites are migrated, delete the normalizers.

7. Dependency boundary: who should import fileLayer

Any module that needs to:

  • Construct a path (help, manifest, script)
  • Load text or JSON
  • Probe existence

…should import fileLayer rather than re-implementing these behaviors.

Typical consumers:

  • manifest.js uses manifest path helpers + loadJSON + exists
  • menu/help code uses helpHtml or helpExists
  • scriptRunner uses script path helpers and/or loadText for “Show Script”

8. Practical examples (how higher layers should use fileLayer)

8.1 ManifestManager style (directoryRegistry model)

// Pseudocode (illustrative only)
const regPath = fileLayer.path.directoryRegistry(basedir);
const hasReg  = await fileLayer.exists(regPath);

if (hasReg) {
  const registry = await fileLayer.loadJSON(regPath);
  // ...then per category:
  const catMan = fileLayer.path.categoryManifest(basedir, category);
  const hasMan = await fileLayer.exists(catMan);
  if (hasMan) {
    const items = await fileLayer.loadJSON(catMan);
  }
}

8.2 Help menu enable/disable

// Pseudocode (illustrative only)
const helpPath = fileLayer.path.helpHtml(tabName, helpKey);
const ok = await fileLayer.exists(helpPath);
// If ok, enable help command. Otherwise disable.

8.3 Script “Show Source” viewer

// Pseudocode (illustrative only)
const scriptPath = fileLayer.path.patternScript(category, filename);
const src = await fileLayer.loadText(scriptPath);
// Then escape and show in offcanvas or overlay.

9. Summary checklist

  • fileLayer is the “mechanics” layer: fetch primitives + path construction.
  • No UI logic, no tab knowledge, no manifest policy in this file.
  • exists is a HEAD probe; it returns false on errors as well as missing files.
  • loadText/loadJSON return null on failure; callers must decide what “failure” means.
  • path helpers are the preferred API; they centralize all path construction rules.
  • legacy normalizers are temporary shims that should disappear after migration.

End of treatise.
