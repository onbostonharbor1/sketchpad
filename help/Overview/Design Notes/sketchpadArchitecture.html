Sketchpad Architecture (Detailed)

This document is the detailed architectural reference for Sketchpad. It is intended to support implementation, debugging, and long-term consistency.

This treatise assumes the core Sketchpad design rules:

  • UI state drives the UI; uiState is updated first, then rendering happens.
  • Each tab is an independent subsystem that owns its regions.
  • Tab activation follows TabSpec init/restore/save rules.
  • Manifests are loaded once, cached, and treated as immutable.
  • Fail-fast everywhere; missing data is a broken state, not a “skip” case.

1. Tab Lifecycle (TabSpec + setUI)

Sketchpad is organized around top-level tabs. Each tab is a self-contained subsystem that is activated through a TabSpec object.

1.1 TabSpec contract

Every tab provides a TabSpec with these core lifecycle methods:

  • init(restoredFlag) — cold-start initializer only
  • restore() — rebuild from saved uiState only
  • save() — snapshot current state before leaving tab

The TabSpec also declares which regions it owns (caption, text, sketchpad, action).

1.2 Cold start vs restore

Sketchpad distinguishes two entry cases:

  • Cold start: the tab has no saved state yet, so it builds its UI from defaults.
  • Restore: the tab has saved state, so it reconstructs exactly what the user was viewing.

Architectural rule: init() must not contain restore logic. restore() must not contain cold-start logic.

1.3 setUI.js responsibilities

setUI.js is the orchestrator. It must:

  • switch active tab
  • apply theme
  • clear regions on cold init
  • call init() or restore()
  • call save() before leaving a tab

Architectural rule: setUI.js does not render tab content. It only delegates to the active tab’s controller logic.

2. uiState (Authoritative UI State)

uiState is the authoritative record of what the user is looking at right now. It is the only “truth source” for restore behavior.

2.1 uiState as the driver

Sketchpad follows the rule:

User action → uiState update → rendering

Rendering never “discovers” state by reading the DOM. State is written first and then the DOM is rebuilt.

2.2 Saved state snapshots

Each tab maintains a saved snapshot:

uiState.<tab>.saved

This snapshot must contain enough information to reconstruct the exact view:

  • view type (categories vs results vs object workspace)
  • active category name
  • active index or item identity
  • active subtab if the tab has internal subtabs

Architectural rule: restore() uses only uiState.<tab>.saved. It must not rely on scattered flags or implicit UI state.

3. Manifest Layer (manifest.js + cache rules)

Manifests define content inventory. They are the authoritative “what exists” layer for file-based tabs.

3.1 What manifest.js owns

manifest.js provides:

  • loading JSON manifests by tab/domain name
  • loading directory registries
  • caching loaded results
  • explicit cache invalidation

3.2 Cache rules

Architectural rules:

  • Manifests are loaded once and cached.
  • Cached manifest data is treated as immutable.
  • Tabs only read cached data.
  • Cache is invalidated only when a maintenance task changes inventory.

3.3 Why immutability matters

Treating manifest cache as immutable prevents subtle drift between:

  • what the UI believes exists
  • what the filesystem actually contains

When a maintenance task changes the filesystem, the correct response is:

  1. invalidate cache
  2. reload manifest
  3. restore view from uiState

4. Categories Rendering (categories.js descriptor contract)

categories.js is a pure renderer for category frames and items. It is intentionally ignorant of tabs, manifests, and filesystem structure.

4.1 Input descriptor format

Tabs pass an array of frames, where each frame contains:

  • frame title
  • items array

Each item includes:

  • display name
  • hasSubitems flag (optional)
  • onClick handler (required)

4.2 Why this matters

This design keeps category rendering stable while tabs evolve independently.

Architectural rule: categories.js does not “decide behavior.” Tabs decide behavior by wiring onClick handlers.

5. Caption Bar (caption.js + navigation + menus)

caption.js builds the caption bar for the active view. It is a shared UI component used across multiple tabs.

5.1 Responsibilities

caption.js is responsible for:

  • displaying a title string
  • wiring Prev / Next buttons when provided
  • opening a menu when provided
  • optionally enabling the Next/Prev click-zone overlay

5.2 Overlay target anchoring

Some views display content in #text (images). Some views display content in #sketchpad-wrapper (canvas host).

The caption bar must specify which region receives the overlay:

  • overlayTargetId = "text"
  • overlayTargetId = "sketchpad-wrapper"

Architectural rule: caption.js becomes the single on/off switch for the overlay.

5.3 Menu wiring

The caption menu is invoked by passing an onMenu callback:

  • tab builds an info object describing current selection
  • tab asks a per-tab menu builder for menu items
  • menuManager opens the menu anchored to the caption control

6. Menus (menuManager + per-tab menuCmds shaping)

Sketchpad menus are structured so that:

  • tabs shape context
  • shared commands perform work

6.1 menuManager.js

menuManager owns:

  • menu rendering
  • menu positioning
  • closing behavior

6.2 Per-tab menu builders

Each tab provides a function like:

getPatternsCaptionMenuItems(info)

This function converts the current view context into menu items.

6.3 Shared menu commands

Shared menu command modules perform:

  • nodeDispatch calls
  • overlay open/close
  • manifest cache invalidation
  • UI refresh from uiState

Architectural rule: per-tab menu modules should be thin “shapers.”

7. Script Execution (runPattern + scriptRunner)

Script execution is the bridge between:

  • file-based content inventory
  • drawRegistry-like runtime behavior

7.1 runPattern() as the canonical entry point

runPattern() is the orchestrator entry point for Sketchpad scripts.

Required runPattern sequence:

  1. printTitle(scriptInfo.title)
  2. alias setup: scriptInfo.parameters = scriptInfo.params
  3. init() called once
  4. buildParameterControls(scriptInfo, targetId, true)
  5. explicit first draw (usually redrawHandler)

Architectural rule: runPattern() contains no drawing math.

7.2 scriptRunner.js responsibilities

scriptRunner handles:

  • importing modules by path
  • executing the correct entry point
  • providing consistent error behavior

scriptRunner must not:

  • mutate uiState
  • interpret tab-specific meaning
  • make manifest decisions

8. drawRegistry Architecture (init/update/draw + elements)

drawRegistry entries are internal “first-class objects.” They are defined as predictable window globals and follow a uniform lifecycle.

8.1 The registry object shape

A typical entry includes:

  • metadata fields (name, id, category, tags, description)
  • visual fields (background, overlays, transforms)
  • params (JSON-safe defaults)
  • controls (UI metadata)
  • elements (runtime objects)
  • init/update/draw functions

8.2 elements as persistent runtime state

elements must be created once in init() and then mutated.

Canonical shape:

elements = { element: { ... } }

draw() reads only from elements.element. It does not read directly from params.

8.3 update(params) rules

update(params) is responsible for:

  • copying values into elements.element
  • type normalization (numbers, booleans, points)
  • validation (fail-fast)
  • recomputing derived values

update(params) must not:

  • draw
  • build UI
  • create a new element object

9. File Identity + Paths (fileLayer.js)

Sketchpad depends on correct file identity and correct path construction. A large class of failures occur when “the UI thinks a file is X” but the filesystem path is actually Y.

9.1 Why fileLayer.js exists

Sketchpad contains multiple content trees:

  • /patterns/<category>/
  • /gallery/<Domain>/<Category>/
  • /home/ (rooted references into other trees)
  • /utilities/

fileLayer.js exists to enforce consistent identity rules across these trees.

9.2 Canonical identity rules

Identity rules must define:

  • what string is used to match a manifest entry
  • what string is used as filename
  • what string is used as a script import path

If these do not match, menu commands like archive/edit will fail.

10. Node Dispatch (nodeLayer.js)

The browser cannot directly perform filesystem operations. Node dispatch provides the bridge.

10.1 Dispatch request structure

A dispatch request contains:

  • requestName
  • payload

The payload must be shaped by the active tab using uiState context.

10.2 Node dispatch responsibilities

nodeLayer.js must:

  • send the request to the service endpoint
  • handle HTTP errors as fail-fast
  • return structured JSON results

nodeLayer.js must not:

  • guess UI meaning
  • perform DOM updates
  • hide errors

Back to Mini-TOC

11. Node Service (sketchpadService.mjs)

sketchpadService.mjs is the central Node service that executes filesystem tasks.

11.1 Service role

The service:

  • receives dispatch requests
  • executes a named task
  • writes files or performs maintenance
  • returns a structured result

11.2 Result structure

Results must include enough information for the UI to:

  • invalidate caches if needed
  • restore the correct view from uiState
  • display logs or reports deterministically

Architectural rule: Node service does not “refresh UI.” The UI refreshes itself.

12. Manifest Maintenance (maintain_manifests.mjs)

maintain_manifests.mjs is the authoritative inventory maintenance script. It ensures that the UI inventory matches the filesystem inventory.

12.1 What it does

  • scan directories
  • detect categories and items
  • generate or update manifest.json files
  • validate expected fields
  • report added/broken entries

12.2 Why it matters

Without maintenance, Sketchpad can drift into broken states:

  • manifest entries pointing to missing files
  • files existing on disk but not in manifests
  • thumbnails missing for new items
  • Home entries referencing stale paths

Architectural rule: tabs do not “repair” inventory; maintenance scripts do.

13. Per-Tab Ownership Summary

Each tab owns its own regions and behavior. Cross-tab UI modification is not allowed.

13.1 Draw Tab

  • inventory: drawRegistry
  • rendering: canvas-based objects
  • controls: parameterControls driven by controls metadata

13.2 Patterns Tab

  • inventory: patterns manifests
  • rendering: imported scripts executed on canvas
  • navigation: categories + results view + thumbnails

13.3 Gallery Tab

  • inventory: per-domain registries + per-category manifests
  • rendering: images in #text OR scripts in canvas
  • navigation: domain tabs + shared Results tab

13.4 Utilities Tab

  • inventory: tools, scripts, reports
  • rendering: text reports + canvas scripts
  • role: system inspection and maintenance

13.5 Home Tab

  • inventory: generated home manifest
  • rendering: images or scripts by extension
  • role: curated index into other content trees

14. Diagnostics and Failure Modes (Debug Map)

Sketchpad is fail-fast by design. Missing data is a broken state and must crash loudly.

14.1 Common failure signatures

Examples:

  • “Missing manifest.json” → inventory is broken or a path is wrong.
  • “Results tab clicked but no saved results context exists” → uiState.saved is inconsistent with the UI.
  • “source file not found” → manifest identity mismatch (path/filename mismatch).
  • “script module missing expected exports” → script is not conforming to the expected runPattern contract.

14.2 Debugging principle

Because the system is deterministic, the first thrown error is usually the best one. Fix the earliest boundary where state and reality diverged.

15. Cross-Functional Flows (End-to-End Handoffs)

The subsystem pages explain “what each file owns.” This section explains the end-to-end flows that cut across multiple files. These are the places where responsibility hands off and where most real bugs occur: the UI context must be shaped correctly, identity must be canonical, caches must be invalidated explicitly, and refresh must be driven by uiState restore logic.

Canonical template used below
Purpose → Trigger → Canonical data object → Sequence → Invariants → Failure signatures → Where to debug first

15.A Caption menu command flow (caption → menu → node → cache → refresh)

Purpose: Execute a command on the currently displayed item (archive/edit/thumbnail/etc.) with correct identity and deterministic UI refresh.

Trigger: User opens the caption menu and selects a command.

Canonical data object: An “info object” built by the active tab that contains:

  • domain/category (or tab-specific equivalent)
  • manifestPath
  • matchField and matchValue (canonical identity)
  • filename (canonical file identity string, including extension)
  • optional scriptPath (when a script file is the target)
  • helpKey/helpSubdirs (for Help integration)

Sequence (handoff chain):

  1. Tab computes current selection from uiState and/or tab-local state.
  2. Tab builds the info object and passes it into its per-tab menu builder.
  3. Per-tab menu builder returns menu items (label + onClick handlers).
  4. menuManager renders the menu and invokes the selected handler.
  5. Shared menu command calls nodeLayer (nodeDispatch) with requestName + payload.
  6. sketchpadService.mjs executes the task (may call maintain_manifests.mjs or file ops).
  7. Result returns to browser as structured JSON (and possibly a log name).
  8. UI invalidates relevant manifest caches explicitly.
  9. UI refreshes by reloading manifest and restoring view from uiState (not “DOM discovery”).

Invariants:

  • matchField/matchValue must match the actual manifest entry field and value (no guessing).
  • filename must be the canonical identity string (including extension).
  • Cache invalidation must happen before any reload/restore step.
  • Refresh must be driven by uiState.saved; do not invent a new navigation policy mid-command.

Failure signatures:

  • “source file not found” → payload identity/path mismatch (often fileLayer normalization mismatch).
  • “manifest entry not found” → matchField/matchValue mismatch or cache not invalidated.
  • command appears to work but UI still shows old list → cache invalidation missing or wrong cache key cleared.

Where to debug first: Inspect the built info object (especially matchField/matchValue and manifestPath) and compare it to the manifest entry on disk.

15.B Commands offcanvas flow (Commands button → maintenance → refresh)

Purpose: Run a maintenance task (rebuild/validate manifests, etc.) via an offcanvas panel and return to a correct, refreshed view.

Trigger: User clicks the global Commands button, then clicks a command inside the offcanvas.

Canonical data object: The offcanvas command handler uses:

  • requestName + payload (often empty for global maintenance tasks)
  • the tab’s refresh policy (usually “invalidate cache, reload, restore from uiState.saved”)

Sequence (handoff chain):

  1. Tab wires Commands button using ui_utilities.js helpers.
  2. showCommandsOffcanvas renders HTML and exposes button IDs.
  3. Tab command handler calls nodeRebuildAndValidateManifests (nodeLayer request).
  4. Service runs maintain_manifests.mjs (or equivalent) and returns report/log.
  5. Tab invalidates the relevant manifest caches explicitly.
  6. Tab reloads manifests and restores view from uiState.saved (categories/results/etc.).
  7. Tab formats and displays the report in the offcanvas panel.

Invariants:

  • Offcanvas HTML IDs must exist (fail-fast if missing).
  • Refresh must not overwrite uiState.saved; it must use it.
  • Cache invalidation must precede reload.
  • Results view restoration must rebuild the same selection and caption.

Failure signatures:

  • “#...Button missing” → offcanvas HTML does not define expected IDs.
  • After maintenance, Results tab breaks → uiState.saved not preserved or overwritten during refresh.
  • Inventory appears unchanged → cache invalidation missing or performed against the wrong cache key.

Where to debug first: Confirm cache invalidation happens, then confirm restore path reads uiState.saved rather than constructing a new default.

15.C Manifest identity rules across domains (Patterns vs Gallery vs Home)

Purpose: Ensure that “the string used to identify an item” is consistent across: display, manifest matching, filesystem path resolution, and node tasks.

Trigger: Any action that targets a specific item: archive, rename, edit title, delete, thumbnail generation, “open in offcanvas,” etc.

Canonical data object: A domain-specific identity triple:

  • manifestPath (which manifest file contains the entry)
  • matchField (which field is authoritative for identity)
  • matchValue (the canonical identity string; must match the manifest exactly after normalization rules)

Sequence (handoff chain):

  1. UI selects an entry (often containing title/filename/path).
  2. Tab converts the entry into the canonical identity triple (via fileLayer rules as needed).
  3. Node task uses the identity triple to find the manifest entry and locate the source file.

Invariants:

  • matchValue must be the canonical identity string; do not mix “display title” with “file identity.”
  • Any normalization (such as stripping redundant category prefix) must be applied consistently everywhere.
  • Home is a rooted cross-tree index; its entries must preserve enough path context to resolve back into the correct tree.

Failure signatures:

  • “source file not found” → identity string looks correct to the UI but is not the real filesystem path.
  • Node reports “entry not found” → matchField/matchValue does not align with the manifest schema for that domain.
  • Thumbnail paths look wrong → a second, non-canonical “filename” string is being used for derived assets.

Where to debug first: Inspect the manifest entry on disk and confirm which field is the identity field for that domain. Then confirm the UI’s matchValue matches it exactly (after any documented normalization).

15.D Tab lifecycle and restore contract (setUI ↔ TabSpec ↔ uiState.saved)

Purpose: Ensure that switching tabs or re-entering a tab always reconstructs the same view deterministically.

Trigger: Tab switch, app reload, or post-maintenance refresh that re-enters a tab.

Canonical data object: The per-tab snapshot: uiState.<tab>.saved

Sequence (handoff chain):

  1. Leaving tab: setUI calls tab.save() (or the tab updates uiState.saved continuously).
  2. Entering tab: setUI decides init vs restore solely from uiState.<tab>.saved existence/meaning.
  3. Cold init: tab.init builds UI from defaults and writes uiState.saved.
  4. Restore: tab.restore reads uiState.saved and rebuilds view exactly.

Invariants:

  • init() must not “fix up” restore behavior.
  • restore() must not “assume defaults.”
  • uiState must be written first, then the DOM is built.
  • Tabs own their regions; restore does not reach across into other tabs’ UI.

Failure signatures:

  • “Results tab clicked but no saved results context exists” → UI allowed a path into restore without a valid uiState.saved.
  • Tab comes back in the wrong subtab → uiState.saved is missing activeSubtab, or restore ignores it.
  • After maintenance, tab returns to categories unexpectedly → refresh overwrote uiState.saved instead of using it.

Where to debug first: Print uiState.<tab>.saved at the moment restore is invoked and compare it to what the UI is showing.

15.E Script execution lifecycle (tab selection → import → runPattern → parameterControls)

Purpose: Execute a script deterministically with consistent UI controls and redraw behavior, regardless of which tab launched it.

Trigger: User selects a script-like item (Patterns entry, Gallery script entry, Utilities script, Home script entry).

Canonical data object: The script module plus the runPattern contract:

  • moduleUrl (canonical import path)
  • exports: scriptInfo + runPattern (or the expected alternative exports for legacy scripts)
  • scriptInfo: title + controls + params + redrawHandler bridge

Sequence (handoff chain):

  1. Tab resolves a moduleUrl (using correct identity/path rules).
  2. scriptRunner imports the module by moduleUrl.
  3. scriptRunner invokes runPattern() as the entry point (canonical path).
  4. runPattern prints title, prepares compatibility aliases, calls init(), builds controls, performs first draw.
  5. parameterControls calls redrawHandler when controls change.
  6. redrawHandler calls update(params) then draw().

Invariants:

  • runPattern is the orchestrator and does not contain drawing math.
  • draw reads only from elements.element; it does not read params directly.
  • update normalizes types and validates; update must not draw.
  • The moduleUrl must be correct for the active tab’s tree.

Failure signatures:

  • “script module missing expected exports” → module does not conform to the required interface.
  • Controls change but nothing redraws → redrawHandler missing or not wired to update/draw.
  • Initial display is blank → runPattern did not perform an explicit first draw.

Where to debug first: Confirm moduleUrl resolves, then inspect module exports, then confirm redrawHandler is present and calls update/draw.
