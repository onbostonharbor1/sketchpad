runPattern() in Sketchpad

This document explains the role, contract, and expected behavior of runPattern() as used throughout Sketchpad.

In Sketchpad, runPattern() is the canonical entry point for running a drawing script. It is not a general-purpose “draw function.” It is an orchestrator that:

  • initializes persistent runtime state (elements)
  • connects UI controls (parameterControls) to that state
  • triggers a deterministic first render

Where runPattern() is used

Sketchpad executes scripts from multiple places (Patterns, Gallery Scripts, Utilities Lab, and Home). Regardless of where the script originates, the execution flow is the same: the loader imports the module, then calls runPattern().

The loader (for example, scriptRunner.js or a tab controller) is responsible for:

  • attaching the shared canvas to the correct region (#sketchpad)
  • clearing the canvas to a known background (typically white)
  • calling runPattern() with the expected signature for that subsystem

The script itself is responsible for everything else.

runPattern() is the orchestrator

runPattern() exists to enforce a single predictable lifecycle:

  1. present title (human context)
  2. create runtime elements (persistent objects)
  3. build UI controls (parameterControls)
  4. perform first draw (explicit)

The key design principle is separation of responsibilities:

  • init() creates objects
  • update(params) applies new values
  • draw() renders deterministically
  • runPattern() ties them together in the correct order

Canonical script model used by runPattern()

Sketchpad prefers scripts that follow the same vocabulary as drawRegistry entries, even when they are not actually drawRegistry items.

A compatible module typically contains:

  • scriptInfo (metadata + UI contract)
  • params (JSON-safe defaults + current UI values)
  • controls (parameterControls schema)
  • elements (persistent runtime state)
  • init() (cold-start only)
  • update(newParams) (apply new values, do not draw)
  • draw() (render only, do not read params)
  • runPattern() (orchestrator)

runPattern() required sequence

A canonical runPattern() must perform these steps in order:

  1. printTitle(scriptInfo.title)

    The script title is printed to the UI (or overlay) so the user knows what is running.

  2. Compatibility alias setup

    parameterControls currently expects scriptInfo.parameters. If the script uses scriptInfo.params, it must alias: 

    scriptInfo.parameters = scriptInfo.params
  3. init()

    Called exactly once per script load. This creates elements and seeds elements.element from params.

  4. buildParameterControls(scriptInfo, targetId, true)

    This builds the controls UI from scriptInfo.controls and binds user changes to the script’s redraw behavior.

    The targetId is owned by the Sketchpad UI layout and must not be changed by the script.

  5. First draw (explicit)

    A correct script must always do an explicit first render. The typical pattern is: 

    scriptInfo.redrawHandler();

ParameterControls compatibility bridge

Sketchpad’s parameterControls expects a specific interface on scriptInfo. To keep conversions mechanical and low-risk, scripts provide a bridge.

The required bridge fields are:

  • scriptInfo.title
  • scriptInfo.controls
  • scriptInfo.parameters (alias to params)
  • scriptInfo.redrawHandler
  • scriptInfo.onParamChange (may be no-op)

The canonical redraw handler is: 

scriptInfo.redrawHandler = function () {
  update(this.params);
  draw();
};

This preserves the required separation:

  • controls mutate params
  • update copies params into elements.element
  • draw reads elements.element and renders

What runPattern() must NOT do

A correct runPattern() must never:

  • create or resolve ctx (ctx is global and must already exist)
  • accept a ctx parameter
  • cache or alias ctx
  • do drawing logic itself (drawing belongs in draw())
  • mutate controls

Common failure modes

Controls move but nothing redraws

Cause: missing or broken scriptInfo.redrawHandler.

Drawing ignores control values

Cause: draw() is reading from params or stale locals instead of reading from elements.element.

Blank initial render

Cause: runPattern() did not do an explicit first draw.

Wrong numeric behavior

Cause: type normalization missing in update() (range controls deliver strings unless converted).

Minimal canonical runPattern() example

This is a minimal structural example. It shows the required ordering and the compatibility bridge. The math/drawing inside draw() is intentionally omitted. 

export const scriptInfo = {
  title: "Example Script",
  params: {
    radius: 100
  },
  controls: {
    radius: { widget: "range", min: 10, max: 300, step: 1, label: "Radius:" }
  }
};

export let elements = null;

export function init() {
  elements = { element: { radius: scriptInfo.params.radius } };
}

export function update(newParams) {
  elements.element.radius = Number(newParams.radius);
}

export function draw() {
  // draw using ctx and elements.element only
}

export async function runPattern() {
  printTitle(scriptInfo.title);

  // Compatibility alias for parameterControls
  scriptInfo.parameters = scriptInfo.params;

  scriptInfo.redrawHandler = function () {
    update(this.params);
    draw();
  };

  scriptInfo.onParamChange = function () {
    // optional no-op; may be required by parameterControls
  };

  init();

  buildParameterControls(scriptInfo, "action", true);

  scriptInfo.redrawHandler();
}

Summary

In Sketchpad, runPattern() is the single canonical entry point for running a script. It exists to enforce a deterministic lifecycle and keep drawing scripts structurally consistent with drawRegistry.

If a script follows the init/update/draw model and provides the parameterControls compatibility bridge, it will run predictably in Patterns, Gallery Scripts, Utilities Lab, and Home.
