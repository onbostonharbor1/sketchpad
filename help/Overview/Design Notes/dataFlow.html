Sketchpad Data Flow (Overview)

This document describes Sketchpad data flow at a conceptual level.

Note: “data flow” in Sketchpad is a broad concept. Sketchpad is not a single pipeline system. It is a collection of cooperating subsystems (tabs, manifests, UI state, drawing runtime objects, overlays, and Node services) that exchange data in predictable ways.

This treatise is therefore an overview, not an exhaustive formal specification.

1. The major data domains in Sketchpad

Sketchpad has several distinct kinds of “data,” each with a different lifetime and purpose.

A. UI State (uiState.js)

UI state is the authoritative record of “what the user is looking at right now.”

  • active tab
  • active category
  • active item
  • active subtab
  • saved view context (categories vs results)
  • last selected index for restoration

UI state changes immediately when the user clicks something. Rendering follows state, not the other way around.

B. Manifest Data (directoryRegistry.json + manifest.json)

Manifests are the authoritative inventory of content:

  • which categories exist
  • which items exist inside each category
  • titles, filenames, paths, metadata fields

Manifests are loaded once, cached, and treated as immutable. Tabs only read cached manifest data.

C. Runtime Drawing State (elements / params / controls)

This is the “live” drawing state used while a script or drawRegistry entry is running.

  • params: current UI values (JSON-safe)
  • controls: declarative metadata for UI generation
  • elements: persistent runtime objects used by draw()

Runtime drawing state is created on entry (init) and mutated by update(). The draw() function reads from elements only.

D. Node Service Data (filesystem + generated reports)

Sketchpad includes a Node-side service layer that performs filesystem operations and maintenance tasks. Node tasks produce structured results and log output.

Examples include:

  • rebuild and validate manifests
  • write thumbnails
  • archive scripts or items
  • edit manifest titles

Node tasks do not directly manipulate the UI. They return data to the browser, and the browser decides how to display it.

2. The four primary data-flow loops

Sketchpad can be understood as four main loops. Each loop is deterministic and has a clear “owner.”

Loop 1: UI Navigation Flow (click → uiState → render)

This is the core “UI drives UI” rule.

  1. User clicks a tab, category, item, or subtab.
  2. The tab controller updates uiState immediately.
  3. The tab controller renders the correct view based on uiState.

The key principle is: uiState is always updated first, then rendering happens.

Loop 2: Content Inventory Flow (filesystem → manifest cache → UI)

Manifests define what content exists and how it is organized.

  1. On cold start, a tab loads its required manifests.
  2. Manifests are cached in memory (manifest.cache).
  3. UI rendering reads from the cached data only.

In normal operation, tabs do not repeatedly fetch manifest files. The cache is treated as authoritative until explicitly invalidated.

Loop 3: Drawing Flow (controls → params → update() → elements → draw())

This is the canonical drawRegistry-like lifecycle used by scripts and objects.

  1. parameterControls renders UI controls based on controls metadata.
  2. Control interaction updates params.
  3. redrawHandler calls update(params) to apply changes to elements.element.
  4. draw() renders deterministically from elements.element.

The key principle is: draw() does not read params directly.

Loop 4: Maintenance Flow (UI → nodeDispatch → service → UI refresh)

This is the “system maintenance” loop used for tasks like rebuild, archive, edit, and thumbnail generation.

  1. User invokes a maintenance command (menu item or offcanvas button).
  2. Browser calls nodeDispatch with a request name and payload.
  3. Node service performs filesystem work and returns structured results.
  4. Browser invalidates caches if needed.
  5. Browser restores the tab view from uiState.

The key principle is: Node work changes files, but the browser decides how to reflect that change.

3. Data flow by subsystem (high-level map)

Each Sketchpad tab is an independent subsystem. Each subsystem follows the same architectural rules, but reads different data sources.

A. Draw Tab

  • Inventory source: drawRegistry (internal JS objects)
  • State source: uiState.draw
  • Runtime source: drawRegistry entry elements + params

Draw Tab is “object driven” rather than “file driven.”

B. Patterns Tab

  • Inventory source: /patterns/<category>/manifest.json
  • State source: uiState.patterns
  • Runtime source: imported module runPattern()

Patterns is “file driven,” but scripts are expected to behave like drawRegistry objects when executed.

C. Gallery Tab

  • Inventory source: /gallery/<Domain>/directoryRegistry.json and per-category manifests
  • State source: uiState.gallery
  • Runtime source: images or imported script modules

Gallery contains both static content (images) and executable content (scripts).

D. Utilities Tab

  • Inventory source: Utilities manifests (and/or hardwired scripts)
  • State source: uiState.utilities
  • Runtime source: scripts + node service reports

Utilities is the “system workbench.” It is where maintenance and inspection tasks are exposed.

E. Home Tab

  • Inventory source: /home/manifest.json (generated by Node)
  • State source: uiState.home
  • Runtime source: scripts (runPattern) and images

Home is a curated index, not a content storage system. It points into other parts of the filesystem by rooted path.

4. What makes Sketchpad “fail-fast”

Sketchpad is intentionally designed to crash loudly when required data is missing. This is not a bug; it is a development strategy.

Examples of fail-fast conditions:

  • required DOM regions are missing
  • manifest files are missing or unreadable
  • uiState saved context is missing or inconsistent
  • a script does not export expected fields
  • an item path is malformed

Fail-fast behavior makes the data flow visible: the console error shows the exact boundary where state and reality diverged.

5. Typical end-to-end flows

Flow A: Select a Pattern and run it

  1. User selects Patterns tab.
  2. Patterns tab reads cached manifest inventory.
  3. User selects a pattern item.
  4. uiState.patterns is updated to results view.
  5. The module is imported.
  6. runPattern() builds controls and draws.

Flow B: Browse Gallery images

  1. User selects Gallery tab and a domain (Ideabook / Patterns / Scripts).
  2. Gallery reads cached per-domain manifests.
  3. User selects an item.
  4. uiState.gallery.saved is updated to results view.
  5. Caption bar prev/next navigates by updating index and re-rendering.

Flow C: Maintenance task (Rebuild & Validate)

  1. User opens Commands offcanvas.
  2. User clicks Rebuild & Validate.
  3. UI calls nodeDispatch.
  4. Node service updates manifests and returns report.
  5. UI invalidates cache and restores current view from uiState.
  6. UI displays report output.

6. What this document does NOT specify

This overview does not attempt to define every file and every function. Sketchpad is intentionally modular and each subsystem owns its own internal details.

Topics not fully specified here include:

  • exact manifest schemas per tab
  • exact overlayManager layer flow
  • caption bar and menu item wiring details
  • future persistence (Dexie) for drawRegistry objects
  • future figure objects and interconnections

Those are best handled as separate treatises.

Summary

Sketchpad data flow is best understood as multiple deterministic loops:

  • UI navigation flow: click → uiState → render
  • content inventory flow: filesystem → manifests → cache → UI
  • drawing flow: controls → params → update → elements → draw
  • maintenance flow: UI → nodeDispatch → service → UI refresh

These loops interact, but they remain separate. This separation is what keeps Sketchpad understandable, testable, and fail-fast.
