How Sketchpad drawRegistry Files Are Organized and Used

This document describes the purpose, structure, and execution flow of a single drawRegistry entry file in Sketchpad.

A drawRegistry file defines one “first-class drawable object”: a reusable, parameter-driven drawing unit that can be selected in the Draw tab, manipulated via controls, and rendered deterministically onto the shared canvas.

The sample file used throughout this discussion is: drawRegistry/mysticRose.js

1. What a drawRegistry File Is

A drawRegistry file is a JavaScript module that registers a single drawing object on the global window namespace using a stable naming convention: 

window.drawRegistry_mysticRose = { ... };

The name drawRegistry_mysticRose is not cosmetic: it is the lookup handle Sketchpad uses when building category lists and when instantiating the object at runtime.

Each registry entry is an object with:

  • metadata (identity, category, tags, description)
  • JSON-safe defaults (params)
  • UI control descriptors (controls)
  • a small lifecycle (init(), update(), draw())
  • persistent elements (elements) created once and reused

2. Sample Registry Entry: Mystic Rose

The example below is a typical drawRegistry file in Sketchpad: 

/* drawRegistry/mysticRose.js */
import { Point, StringThing }       from '../classes/classes.js';
import { drawMysticRose }           from '../draw/drawUnicorns.js';

window.drawRegistry_mysticRose = {
    name:         "Mystic Rose (circle)",
    id:           "mysticRose",
    version:      0.1,
    category:     "unicorns",
    firstOrder:   true,
    source:       "internal",
    tags:         ["circular"],
    description:  "Lines drawn to all nodes from each node in a circle",
    status:      "",
    hover:        "",

    // -- visual styling ---
    background: null,
    overlays:   [],
    transforms: [],

    // Placeholder for all elements drawn
    elements:   null,

    // --- Core defaults for drawing (JSON-safe) ---
    params: {
      midpoint: { x: 300, y: 200 },   // converted to Point in init()
      radius:   250,
      numNodes: 20,
      xScale:   1,
      yScale:   1,
      color:    "blue",
      lineWidth: 1
    },

    // --- UI metadata (controls) ---
    controls: {
      radius:    { widget: "range", min: 80,  max: 500, step: 5,   label: "Radius:" },
      numNodes:  { widget: "range", min: 12,  max: 30,  step: 1,   label: "Nodes:" },
      xScale:    { widget: "range", min: 0.5, max: 2,   step: 0.1, label: "X Scale:" },
      yScale:    { widget: "range", min: 0.5, max: 2,   step: 0.1, label: "Y Scale:" },
      color:     { widget: "colorPicker",                          label: "Color:" },
      lineWidth: { widget: "range", min: .5,  max: 3.5, step: .5,  label: "Width:" },
      midpoint:  { widget: "pointPicker",                          label: "Midpoint:" }
    },

    init() { ... },
    update(params) { ... },
    draw() { ... }
};

The remainder of this treatise explains how Sketchpad expects each section to behave.

3. Identity and Metadata Fields

A drawRegistry entry begins with identity and descriptive metadata. These fields are used by the Draw tab UI and by future persistence and search features.

3.1 Display and Identity

  • name
    Human-readable display name used in category lists and captions.
  • id
    A stable internal identifier for the object type. This is intended to remain constant even if the display name changes.
  • version
    A numeric version for the registry entry definition. This can be used later for migration of saved objects.
  • category
    The Draw tab category the entry belongs to. This is the primary grouping key.

3.2 Classification / System Fields

  • firstOrder
    A flag indicating that this is a first-class object intended for direct use in Draw and later Figures. (This is conceptual and UI-driven.)
  • source
    Indicates where the object definition comes from (example: internal).
  • tags
    A small array of search keywords. Example: ["circular"].
  • description
    A one-sentence description of what the object draws.

3.3 Status and Hover (Optional Display Fields)

  • status
    A short status string (often blank). This can be used later for filtering, “new/working/finished” marking, etc.
  • hover
    A short hover hint string. This can be used later in UI overlays.

4. Styling / Rendering Policy Fields

Many drawRegistry entries include placeholders for rendering policy:

  • background — optional background fill or configuration
  • overlays — optional overlay layers to draw or enable
  • transforms — optional transforms applied to the drawing

In the example: 

background: null,
overlays:   [],
transforms: [],

These are present so the registry entry can eventually become a fully self-contained “drawing recipe,” not just a geometry generator. In early versions they often remain inert.

5. The Two Kinds of State: params vs elements

The most important conceptual split in a drawRegistry entry is:

  • params = JSON-safe values that represent the editable “inputs” to the drawing.
  • elements = persistent runtime objects created once, stored on the entry, and mutated as the drawing changes.

This split is deliberate and supports:

  • persistence (save/load params as JSON)
  • interactive editing (controls modify params)
  • stable objects (avoid recreating geometry every redraw)
  • deterministic rendering (draw reads from a known element graph)

5.1 params: JSON-safe defaults

params must be safe to serialize as JSON. This means: no class instances, no functions, no DOM nodes.

Example: 

params: {
  midpoint: { x: 300, y: 200 },
  radius:   250,
  numNodes: 20,
  xScale:   1,
  yScale:   1,
  color:    "blue",
  lineWidth: 1
},

Note that midpoint is stored as a plain object with x/y rather than a Point instance.

5.2 elements: persistent objects created in init()

elements is the container for persistent runtime objects. In the example, init() creates one element: 

this.elements = { element: new StringThing(this.params) };

This is the “live object” that draw() will render.

6. controls: UI Metadata for parameterControls

The controls object describes how each parameter should be edited. It is a declarative map keyed by parameter name: 

controls: {
  radius:    { widget: "range", min: 80,  max: 500, step: 5,   label: "Radius:" },
  numNodes:  { widget: "range", min: 12,  max: 30,  step: 1,   label: "Nodes:" },
  xScale:    { widget: "range", min: 0.5, max: 2,   step: 0.1, label: "X Scale:" },
  yScale:    { widget: "range", min: 0.5, max: 2,   step: 0.1, label: "Y Scale:" },
  color:     { widget: "colorPicker",                          label: "Color:" },
  lineWidth: { widget: "range", min: .5,  max: 3.5, step: .5,  label: "Width:" },
  midpoint:  { widget: "pointPicker",                          label: "Midpoint:" }
},

The Draw tab reads this metadata and builds the control panel dynamically.

6.1 Widget types in the example

  • range
    Numeric slider with min/max/step.
  • colorPicker
    A color selector that returns a string (example: "blue" or "#0000ff").
  • pointPicker
    A specialized control that allows selecting a point on the canvas (or entering coordinates) and returns either a Point-like object or a Point instance depending on implementation.

The key principle is that controls describes UI behavior, while params contains the current editable values.

7. The Lifecycle: init() → update() → draw()

Every drawRegistry entry implements three core functions:

  • init() — cold-start construction of persistent elements
  • update(params) — apply new values to the persistent elements
  • draw() — render the current element state onto the canvas

This lifecycle makes the object deterministic and repeatable: the same params produce the same drawing, and update() does not depend on hidden external state.

7.1 init(): build persistent geometry and style

init() runs once when the entry becomes active for the first time. Its job is to convert JSON-safe params into concrete objects. 

init() {
  // Ensure midpoint is a Point object
  const p = this.params.midpoint;
  if (!(p instanceof Point)) this.params.midpoint = new Point(p.x, p.y);

  this.elements = { element: new StringThing(this.params) };
}, // end init

Two important things happen here:

  • The midpoint is converted from a plain {x,y} into a real Point.
  • The registry entry creates a persistent StringThing that will be reused.

7.2 update(params): apply changes from UI controls

update(params) receives a new parameter object from the UI system. It must update the persistent element graph without rebuilding it. 

update(params) {
  const e = this.elements.element;
  for (const key in this.params) {
    const value = params[key];
    if (value === undefined) continue;

    if (key === "midpoint") {
      if (value instanceof Point)
        e.midpoint = value;
      else
        e.midpoint = new Point(value.x, value.y);
    } else if (key == "radius") {
      e.ellipse.a = value;
      e.ellipse.b = value;
    } else {
      e[key] = value;
    }
  }
}, // end update

This update() illustrates a common pattern:

  • loop over known params (not over user input keys)
  • apply only defined values
  • handle special cases explicitly (midpoint conversion, radius mapping)
  • otherwise assign directly

The radius logic shows that the underlying geometry may not map 1:1 to params: 

} else if (key == "radius") {
  e.ellipse.a = value;
  e.ellipse.b = value;
}

This indicates that StringThing internally uses an ellipse model even when the UI is conceptually “radius”.

7.3 draw(): render deterministically

draw() is the simplest function: it renders the current element state. 

draw() {
  const thing = this.elements.element;
  drawMysticRose(thing);
} // end draw

draw() does not rebuild geometry, does not read from UI controls, and does not attempt to “fix” missing state. It assumes init() and update() have produced a valid object graph.

8. How Sketchpad Uses a drawRegistry Entry at Runtime

The typical execution flow when the user selects an entry in the Draw tab is:

  1. Draw tab selects the registry entry object (by category + id)
  2. Draw tab calls entry.init() once (cold-start)
  3. Draw tab builds parameter controls from entry.controls
  4. When a control changes, Draw tab calls entry.update(newParams)
  5. Draw tab calls entry.draw() after update

This yields a consistent model:

  • controls drive params
  • params drive elements
  • elements drive drawing

9. Naming Conventions and File Organization

In Sketchpad, drawRegistry entries typically live under: 

./drawRegistry/

A file name generally corresponds to the registry name suffix: 

drawRegistry/mysticRose.js
window.drawRegistry_mysticRose

This convention keeps the system predictable and easy to debug: when something fails, you can locate the registry entry by name immediately.

10. Practical Debugging Notes

10.1 Fail-fast behavior

The drawRegistry model works best when errors are allowed to surface immediately. If a required element is missing, it should throw rather than silently degrade.

10.2 Common failure points

  • Missing import for a geometry class or draw function
  • params not JSON-safe (class instances embedded in defaults)
  • init() not called before update/draw
  • update() mismatched keys (UI provides keys that are not handled)
  • draw() assumes elements exist but init() never created them

11. Summary: The drawRegistry Contract

A drawRegistry file defines a single drawing object with:

  • stable identity: id, category, name
  • JSON-safe defaults: params
  • UI metadata: controls
  • persistent runtime elements: elements
  • deterministic lifecycle: init() → update() → draw()

This structure supports incremental development: you can begin with one line, then add more geometry and more parameters, while keeping the same lifecycle and mental model.
