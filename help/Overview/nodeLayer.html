nodeLayer.js — Browser-side Bridge to the Node Service

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on one file:

  • ui/nodeLayer.js (browser-side)
Scope of this treatise
1) What nodeLayer.js does and does not do.
2) The single transport primitive: nodeDispatch(requestName, payload).
3) The “thin convenience wrappers” (nodeListLogFiles, nodeReadLogFile, nodeRebuildAndValidateManifests).
4) Failure behavior and how UI code should use results.

1. What nodeLayer is in the Sketchpad architecture

Sketchpad runs UI code in the browser, but some operations are fundamentally “Node-side”: scanning folders, rewriting manifests, writing thumbnails, reading local log files, and so on. The browser cannot do those things directly.

ui/nodeLayer.js exists to provide a single, consistent bridge:

  • The UI calls a function in nodeLayer.js.
  • nodeLayer sends a structured request to the local Node service.
  • The Node service runs the task and returns structured JSON.
  • The UI renders the JSON report (usually into #text in Utilities, or into a tab report panel).
Strict boundary rule
nodeLayer.js does NOT implement tasks.
It only transports requests and returns results.

2. The single transport primitive: nodeDispatch()

The heart of the file is one function: 

export async function nodeDispatch(requestName, payload = {})

Think of nodeDispatch as your “RPC call” (remote procedure call) to the Node service. It takes:

  • requestName — a string identifying which Node task to run
  • payload — an object carrying any task parameters

It always sends the same JSON envelope: 

{
  requestName: requestName,
  payload: payload
}

2.1 Endpoint and method

The service endpoint is hard-coded: 

POST http://localhost:5174/dispatch

The request uses:

  • HTTP method: POST
  • Header: Content-Type: application/json
  • Body: JSON stringified envelope
Why hard-code?
This reflects the intended “local tool” model: Sketchpad runs a known local Node service. If you later want configurability, this file is the single place to introduce it.

2.2 Fail-fast error behavior

nodeDispatch is explicitly fail-fast on HTTP failures:

  • If response.ok is false, it reads the response text and throws an Error.
  • The error message includes the HTTP status, status text, and response body.
throw new Error(
  `nodeDispatch: HTTP ${status} ${statusText}: ${text}`
);
Practical implication
If the Node service is not running, or the endpoint is wrong, or the service rejects the request, the UI will get a thrown error (a visible console error unless the caller catches and renders it).

If HTTP succeeds, it returns: 

return await response.json();
Contract expectation
The Node service is expected to always return valid JSON on success.

3. Higher-level helpers (thin wrappers)

Below nodeDispatch, this file defines a small set of convenience functions:

  • nodeListLogFiles(limit = 10)
  • nodeReadLogFile(name)
  • nodeRebuildAndValidateManifests()

Each wrapper has one job:

  • Choose the correct requestName
  • Build the correct payload shape
  • Return the JSON report from the Node service
Key architectural principle
UI code should call these named helpers instead of sprinkling raw requestName strings everywhere. That keeps your system consistent and makes it easier to rename tasks later.

3.1 nodeListLogFiles(limit)

Calls: 

nodeDispatch("listLogFiles", { limit })

Intended usage:

  • The UI requests a list of available log files.
  • The UI displays the list (for selection) and/or renders it in Utilities.

3.2 nodeReadLogFile(name)

Calls: 

nodeDispatch("readLogFile", { name })

Intended usage:

  • The UI requests the contents of a specific log file.
  • The Node service reads the file and returns content as JSON (likely text content plus metadata).
  • The UI renders it in a viewer area (usually #text).

3.3 nodeRebuildAndValidateManifests()

Calls: 

nodeDispatch("manifestMaintenance", {})

Intended usage:

  • The UI requests the Node service to scan folders and rebuild/validate manifests.
  • The Node service returns a structured report (what changed, what was fixed, what failed).
  • The calling tab invalidates its cached manifest data and reloads (because the browser cannot auto-detect on-disk changes).
Important lifecycle note
Calling this Node task is only half of the operation.
The other half is UI-side cache invalidation + reload. nodeLayer does not do that; the tab/controller must.

4. What nodeLayer assumes about the Node service

nodeLayer makes very few assumptions, but they are strict:

  • The service is reachable at http://localhost:5174/dispatch.
  • The service accepts a JSON envelope with requestName and payload.
  • On success, the service returns valid JSON.
  • On failure, the service returns a meaningful response body (text) so nodeDispatch can include it in the thrown error.
Separation of responsibility
nodeLayer.js does not validate payload schemas. If you want payload validation, it belongs either: 1) in the calling UI code (client-side validation), and/or 2) in the Node service (authoritative validation).

5. How UI code is expected to use results

The usage model is:

  1. Call a nodeXXX() function.
  2. Receive a JSON report object.
  3. Render it in the UI (often as formatted text).

Example pattern: 

import { nodeRebuildAndValidateManifests } from "./nodeLayer.js";

const report = await nodeRebuildAndValidateManifests();
// render report into #text
// then clear/reload caches and refresh the active view
Why “structured JSON” matters
It keeps Node tasks composable and testable: tasks can return detailed data, and the UI can decide how to display it without scraping strings.

6. Summary checklist

  • nodeLayer.js is browser-side transport only: it does not implement any Node tasks.
  • nodeDispatch is the single primitive: POST JSON to the dispatch endpoint and return JSON.
  • Fail-fast: non-OK HTTP responses throw with status + response body.
  • Wrappers provide stable names for Node requests so UI code doesn’t scatter request strings.
  • Cache refresh is not automatic: after maintenance tasks, the calling tab must invalidate and reload its cached manifest data.

End of treatise.
