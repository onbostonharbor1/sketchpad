Home Tab (home.js) — The One Big Topic: What Must Be Understood

This page is a conceptual map for home.js: what it owns, what it reads/writes in uiState, how it moves between “Categories” and “Results,” and how it launches other tabs (especially Draw) using uiState.launch. It is not a line-by-line commentary.

Core idea: Home is a “dispatcher” tab. It reads a single flat manifest (/home/manifest.json), groups by status, displays category frames, and for each item either: (a) runs a script or shows an image in Results, or (b) launches Draw for drawRegistry items using a transient launch intent.

1) Contract Boundaries: Home’s Worlds

1.1 World A: setUI + TabSpec

  • HomeTabSpec advertises name/theme/regions and the lifecycle hooks: init, restore, save.
  • Home is written to be deterministic based on uiState.home.saved.
  • Home uses the shared region model: ["subtabs","sketchpad","caption","text","action"].

1.2 World B: Home manifest + grouping

  • Home loads one file: /home/manifest.json, and requires it be a flat array.
  • Home groups entries by required field entry.status into homeManifestGrouped.
  • Categories view renders one frame per status group using categories.js.

1.3 World C: “Results” execution/rendering

  • If entry.path ends in .js, Home loads the module and runs it into the shared canvas.
  • If entry.path is an image extension (png/jpg/jpeg), Home loads an <img> and displays it in #sketchpad.
  • Anything else is fail-fast.

1.4 World D: Cross-tab launch (Home → Draw)

  • Some Home entries are not runnable in Home. They are “launch-only” drawRegistry items.
  • Home sets uiState.launch (transient intent) and uses dynamic import to call setUI("draw").

2) Home State: What Lives in uiState.home.saved

Home forces a stable saved-state object via ensureHomeSavedState(). This is the state machine “memory” that makes restore deterministic.

Shape:

{
  view: "categories" | "results",
  activeStatus: string | null,
  activeIndex: number | null,
  activeEntry: object | null
}

Discussion point: Home currently treats activeEntry as a raw manifest entry object (not just an id/path). That’s convenient for in-session restore but raises the same “pure data” question as Draw: full reload persistence wants a stable key (usually entry.path).

3) Two-View Model: Categories vs Results

3.1 The view keys

  • HOME_VIEW_CATEGORIES = "categories"
  • HOME_VIEW_RESULTS = "results"

3.2 switchHomeView(viewKey): the view state transition function

Sequence:

  1. Ensure saved state exists.
  2. Write uiState.home.saved.view = viewKey.
  3. Rebuild subtabs (Categories always; Results only if activeEntry exists).
  4. Activate the selected subtab button.
  5. If Categories:
    • Clear caption (Home Categories has no caption bar).
    • Clear #sketchpad and #action.
    • Render categories if grouped data is ready; else show “manifest not loaded yet.”
  6. If Results: call renderHomeResults().

Key topic: Subtab rebuilding is state-driven. The “Results” subtab only exists if uiState.home.saved.activeEntry is truthy. That means Results is not a permanent subtab; it’s an earned/conditional one.

4) Subtabs: How Home Builds Them

4.1 setHomeSubtabs()

  • Clears #subtabs and builds <ul class="nav nav-tabs home-subtabs">.
  • Adds Categories always.
  • Adds Results only if uiState.home.saved.activeEntry exists.
  • Activates the current saved view.

4.2 addHomeSubtabButton()

  • Creates one button and wires it to switchHomeView(viewKey).
  • This is the sole “home-internal navigation” gesture.

Discussion point: Home subtabs are view selectors; Draw subtabs are “open documents.” The similarity is “both are subtabs,” but their semantics differ: Home tabs are modes; Draw tabs are instances.

5) Manifest Load + Grouping: Why Home Has Its Own Cache

5.1 Home-only module cache

  • homeManifestLogged prevents repeated console logging / re-load in normal flow.
  • homeManifestData and homeManifestGrouped hold the in-memory snapshot.

5.2 loadHomeManifestAndLog() + loadHomeManifestAndLog_async()

  • The “front” function is a one-shot kick that calls the async loader.
  • The async loader:
    • Fetches /home/manifest.json using fileLayer.loadJSON().
    • Requires an array.
    • Calls groupHomeEntriesByStatus() which requires each entry to be an object and to have a status.
    • Optionally triggers a categories render if Home is currently in Categories view.

Key topic: Home is intentionally decoupled from manifest.cache (the shared manifest system). Home uses fileLayer.loadJSON("/home/manifest.json") and its own grouping cache instead. That’s not “wrong,” but it is a deliberate architectural line that should be understood.

5.3 refreshHomeCategoriesFromManifestEdit()

  • Explicit refresh path: clears Home’s in-memory cache and reloads with cache-busting query ?v=Date.now().
  • Used after “Edit Manifest” to rebuild category frames from updated statuses.

6) Categories Descriptor: The Click Decision Point

Home categories are built by buildHomeCategoryDescriptor(grouped). This is where Home decides whether an item is:

  • Launch-only (drawRegistry → launch Draw and stay in Home Categories), or
  • Results (store activeEntry and enter Results view).

Decision rules used on click:

  • If entry.sourceType === "drawRegistry":
    • Fail-fast if entry.registryKey is missing.
    • Reset Home’s saved view back to Categories and clear active selection fields.
    • Set uiState.launch intent: pending=true, sourceTab="home", targetTab="draw", sourceType="drawRegistry", registryKey=...
    • Call launchTabViaSetUI("draw") (dynamic import) and return.
  • Otherwise:
    • Write Home selection into uiState.home.saved (status + activeEntry).
    • Enter Results view via switchHomeView("results").
    • Build a Results caption via setHomeCaptionForResult(entry).

Key topic: Home intentionally prevents drawRegistry items from becoming Results. That is a hard boundary: drawRegistry entries are “built-in Draw objects,” not “runnable Home scripts.”

7) Results View: Rendering Scripts vs Images (and Preventing Stale Async)

7.1 The render token mechanism

  • homeResultsRenderToken increments each time Results begins rendering.
  • Async paths (module load, image load) check the token before updating the DOM.
  • This prevents “old click finishes late and overwrites new click” bugs.

This is worth discussing in depth. It’s a concrete, simple concurrency control that keeps the UI deterministic under async imports.

7.2 renderHomeResults(): the Results dispatcher

  • Fail-fast if activeEntry is missing.
  • Fail-fast if sourceType === "drawRegistry" (launch-only guard).
  • Clears #text and #action so categories are not visible.
  • Sets caption for result (setHomeCaptionForResult).
  • Dispatches:
    • JS path → renderHomeJsEntryToCanvas
    • Image path → renderHomeImageEntryToSketchpad
    • Else → visible “Unsupported result type” + throw

7.3 Scripts: clearHomeCanvasAndOverlays() is not optional

Home’s script execution path explicitly resets ctx state:

  • ctx.setTransform(1,0,0,1,0,0)
  • ctx.globalAlpha = 1
  • ctx.globalCompositeOperation = "source-over"
  • Clears and fills white background
  • Clears overlay layer container if present

Key topic: This is the antidote to “two drawings on the canvas” and “clearRect didn’t clear” failures. It encodes the important rule: prior scripts may leave ctx transformed, so clearing must reset the transform first.

7.4 Images: renderHomeImageEntryToSketchpad()

  • Uses an Image() object and awaits load.
  • Checks the render token for staleness.
  • Displays the image with contain-style fit.

8) Caption for Results: setHomeCaptionForResult(entry)

Home Results captions are more complex than Home Categories captions.

What it does:

  • Builds a context bundle (tabName, manifestPath, entryPath, title/file/status, isScript/scriptPath).
  • Uses getHomeCaptionMenuItems(ctxBundle) to build menu items.
  • Injects the full rooted path text into #caption .caption-buttons immediately before the menu button.

Discussion point: This “path injection” is a UI pattern (a custom augmentation of caption.js output). It must track caption.js markup assumptions: existence of .caption-buttons and that the menu button is the last button.

9) Commands Offcanvas: Home Maintenance

  • Home wires the global Commands button to a Home Maintenance offcanvas.
  • It runs nodeRebuildAndValidateManifests(), then clears caches.
  • It forces Home manifest reload with cache-busting and writes the text report.

Key topic: Notice Home clears manifest.clearCache() (the shared cache) and also resets Home’s own homeManifestLogged/homeManifestData/homeManifestGrouped. This is a “two cache world” situation and should be kept explicit.

10) Cross-Tab Launch Helper: Dynamic Import of setUI.js

Home cannot statically import setUI.js because setUI.js imports home.js. So Home uses dynamic import:

  • launchTab(tabKey) awaits import and then calls mod.setUI(tabKey).
  • launchTabViaSetUI(tabKey) returns a promise chain that calls mod.setUI(tabKey).

This is a key design pattern: dynamic import as a deliberate, explicit solution to circular dependency, while staying fail-fast.

11) The One Sentence That Summarizes home.js

home.js is a two-view dispatcher tab: it loads a flat Home manifest and renders status-grouped categories, and on item click it either enters Results (rendering scripts into the shared canvas or images into #sketchpad using a stale-token guard), or it launches Draw for drawRegistry items by writing a transient uiState.launch intent and calling setUI("draw") via dynamic import.
