Patterns Tab (patterns.js) — The One Big Topic: What Must Be Understood

This page is not a line-by-line commentary. It is the conceptual map: the contracts, invariants, and “who owns what” that make patterns.js understandable and debuggable.

Focus: The “hard parts” are not DOM mechanics. The hard parts are the architectural contracts: TabSpec, uiState, manifest caching, and the script execution pipeline.

1) Contract Boundaries: Who Is Allowed To Do What

1.1 PatternsTabSpec vs “Controller”

  • PatternsTabSpec is what setUI.js calls: init(restoredFlag), restore(), save().
  • PatternsController is described as “pure action functions,” but in practice the actions in patterns.js do all three things: write state, touch DOM, and run async work.

What to keep in mind: In the current file, “controller” mostly means “the externally callable actions.” It does not currently mean a strict separation layer.

1.2 Tab Orchestration Contract (setUI.js)

  • init() must be cold-start only (build the tab’s static shell + show default view).
  • restore() must reconstruct the last view deterministically from uiState.
  • save() should return plain data only (no functions, no DOM nodes).

Important discussion point: Your pasted setUI.js does not call any tab’s save() before switching tabs. That means patterns.js is effectively relying on uiState.patterns.saved being continuously maintained during navigation. That can be correct, but it must be recognized as the actual design.

2) The Restore Contract Object: uiState.patterns.saved

The heart of the new architecture is that Patterns is always restorable from a minimal, explicit object: uiState.patterns.saved.

Minimal restore contract fields:

  • saved.view = "categories" or "pattern"
  • saved.activeCategory = category string or null
  • saved.activeItem = index number or null

2.1 Invariants (the rules that must always be true)

  • If view === "categories", then activeCategory == null and activeItem == null.
  • If view === "pattern", then activeCategory is a non-empty string and activeItem is a number.

2.2 The key behavioral rule

Rule: Any action that changes what the user is “looking at” should write uiState.patterns.saved before calling a renderer.

This is what makes restore deterministic and makes debugging possible (“state first, then draw”).

3) The Fixed Subtabs Model

Patterns has fixed subtab IDs: patterns-categories and patterns-pattern.

  • Cold init builds the subtab bar and installs the Categories tab.
  • Selecting a pattern creates (if needed) the Pattern tab and activates it.
  • Restore rebuilds the subtab bar again and then reconstructs view.

Discussion point: Is #subtabs part of “static UI that init owns,” or is it a shared region that may need rebuilding on every activation? In practice, you are rebuilding it in restore. That may be correct, but it should be treated as a deliberate rule, not an accident.

4) The Script Execution Pipeline: loadScriptModule + executeScriptToCanvas

Patterns does not “draw directly.” It loads a module by path and runs it. That pipeline has its own contract and failure modes.

4.1 The path format rule matters

High-leverage topic: Decide what the canonical script path form is.

  • Rooted: "/patterns/Star/foo.js"
  • Relative: "../patterns/Star/foo.js" (currently used in your file)

Your loadScriptModule() tries to normalize, but a relative path like "../patterns/..." becomes "/../patterns/...", which browsers may normalize but can also interact badly with dev-server routing. This is worth standardizing early because it affects probing, “Show Script”, help keys, and error messages.

4.2 Canvas attachment ownership

Concrete issue to understand: Who attaches the shared canvas?

  • showSelectedPattern() appends window.drawCanvas into #sketchpad.
  • executeScriptToCanvas() clears #sketchpad and appends window.drawCanvas again.

This duplication may “work” but it is fragile. It also interacts with “state leak” style bugs. A clean design usually picks exactly one owner for canvas attachment.

5) Manifest Caching: What Patterns Owns and What It Assumes

Patterns uses the manifest system as a read-mostly cache: manifest.cache.patterns is built once and then read for all UI rendering.

Key function: ensurePatternsManifestLoaded()

  • Loads raw manifest data via manifest.get("patterns").
  • Gets category registry via manifest.getRegistry("patterns").
  • Builds manifest.cache.patterns as a map: { categoryName: [entries...] }.

5.1 The sanctioned exception: cache invalidation

The Commands-offcanvas “Rebuild & Validate” action invalidates the cache and reloads it. This is one of the best examples of a controlled “exception” to the immutability idea:

  • Run node maintenance
  • Clear manifest cache
  • Reload
  • Re-render from uiState.patterns.saved

6) The Two-View Model: What Patterns Actually “Is”

From a user-facing standpoint, Patterns is basically two views. This is the simplest mental model.

A) Categories View

  • #text: category frames (cards)
  • #action: empty
  • #sketchpad: empty
  • Subtab bar: Categories active

B) Pattern View

  • #sketchpad: shared canvas attached + one pattern drawn
  • #action: thumbnail grid, selected thumb highlighted
  • #caption: title + Prev/Next + Menu
  • Subtab bar: Pattern active

Why this matters: Most functions in the file are just “switch to one of these views deterministically,” and each view has clear region ownership.

7) The Commands Button Path (Offcanvas) Is a Parallel Subsystem

The Commands button (Patterns Maintenance) is not navigation. It is a maintenance action that forces a re-render of the current view.

  • Open offcanvas
  • Run node rebuild/validate
  • Invalidate cache
  • Reload manifest
  • Re-render the exact view indicated by uiState.patterns.saved.view

Reason it is important: It demonstrates the architecture working correctly: “treat uiState as the source of truth; rebuild UI from it.”

8) Places Where Understanding Requires Noticing Contradictions

8.1 Optional chaining and silent fallbacks (vs fail-fast)

There are places where missing data becomes “empty list” or “no-op return” rather than a crash. If your rule is truly fail-fast, these should be discussed and decided deliberately.

  • manifest.cache.patterns?.[category] || []
  • if (!list.length) return; in prev/next

8.2 Comments that mis-state the real ownership

The comment in restorePatternsTab() says “NO clearing — setUI/initTab already handled that.” But restore is called specifically instead of initTab. So the comment is misleading and should be corrected (or the orchestrator behavior should change).

8.3 Canvas attachment duplication

showSelectedPattern() attaches canvas, then executeScriptToCanvas() clears and reattaches. Decide one owner. Otherwise small future changes can reintroduce “state leak” type bugs.

9) Minimum Tests That Prove patterns.js Works

Cold start: switch to Patterns tab

  • Categories list renders
  • Only Categories subtab exists and is active
  • #action and #sketchpad are empty

Select a pattern:

  • Pattern subtab appears and becomes active
  • Thumbnails appear in #action
  • Selected thumbnail highlight matches active index
  • Caption shows “{category}: {title}” with Prev/Next/Menu
  • Canvas shows exactly one pattern (no remnants)

Prev/Next:

  • Index wraps correctly
  • Caption updates
  • Selected thumb highlight updates
  • Canvas redraws deterministically

Tab swapping restore:

  • Leave Patterns, return to Patterns
  • Restores exactly to last saved view (categories or pattern)

Commands → Rebuild & Validate:

  • Report is displayed
  • Manifest cache invalidated and reloaded
  • Current view is reconstructed from uiState.patterns.saved

10) The One Sentence That Summarizes patterns.js

patterns.js is a two-view UI whose correctness depends on maintaining uiState.patterns.saved as the single source of truth, reading patterns from manifest.cache.patterns, and executing scripts through the shared scriptRunner pipeline.
