Draw Tab (draw.js) — The One Big Topic: What Must Be Understood

This page is a conceptual map for draw.js: the contracts, invariants, and “who owns what” that make the Draw tab predictable and debuggable. It is not line-by-line commentary.

Core idea: Draw is not “one view.” It is a small tab system inside a tab system: a persistent Categories subtab plus N object subtabs, each backed by a drawRegistry entry instance and live parameters.

1) Contract Boundaries: Draw’s Three Worlds

1.1 World A: setUI + TabSpec (top-level orchestration)

  • setUI.js selects the active top-level tab.
  • For Draw, it calls DrawTabSpec.init(...) on cold start, or DrawTabSpec.restore() when saved state exists.
  • Draw must be able to rebuild its visible UI from uiState.draw deterministically.

High-leverage point: In your pasted setUI.js, there is no visible call that saves the outgoing tab state. That means Draw cannot rely on “save on tab switch.” Instead it must maintain uiState.draw continuously as the user interacts.

1.2 World B: drawRegistry entries (the drawing engine contract)

Every object tab wraps a drawRegistry entry. The critical contract is:

  • entry.init() creates default persistent elements (geometry + StringThing style).
  • entry.params holds JSON-safe values used by parameterControls.
  • entry.update(params) applies params to the persistent elements.
  • entry.draw() renders deterministically to the shared canvas using those elements.

1.3 World C: UI plumbing (caption bar + parameterControls + overlays)

  • The caption bar is the “object header” for the active object tab.
  • parameterControls builds controls into #action (Draw uses #action only for controls).
  • overlayManager canvas layers (especially “interaction”) are synced to the canvas and used for point pickers etc.

2) The Draw Subtab Model: What Draw “Is”

Draw is a subtab system inside the Draw top-level tab.

Subtab types:

  • Categories subtab: type = "categories", renders category frames into #text.
  • Object subtab: type = "object", renders a drawRegistry entry to the shared canvas and builds parameter controls.

2.1 The primary state containers

  • uiState.draw.activeSubtab (string tab id)
  • uiState.draw.tabs (map from tabId → tab info)

Each tab info object is approximately:

  • Categories tab: { type: "categories" }
  • Object tab: { type: "object", drawRegistry: entry, dirty, parameters }

Important discussion point: In this file, object tabs store the actual drawRegistry entry object reference under drawRegistry. That is not “pure data.” It is a live object. That may be a deliberate exception, but it has consequences for persistence, reload, and “true restore.”

3) Navigation Inside Draw: switchTab(), addDrawSubtab(), deleteTab()

3.1 switchTab(tabId)

  • Updates the UI: active marker on the clicked subtab button.
  • Writes state: uiState.draw.activeSubtab = tabId.
  • Clears shared regions via clearDivs().
  • Dispatches:
    • Categories → renderDrawCategories()
    • Object → drawActiveTab()

What to discuss: This is the Draw equivalent of the “two view model” from Patterns, except Draw has “Categories view” and “Object view,” and Object view is per-subtab.

3.2 addDrawSubtab(item)

This is the creation point for both kinds of subtabs.

  • Builds the subtab DOM button.
  • Creates a tabId: "tab-" + normalized(item.name).
  • If Categories: stores { type: "categories" } and renders categories.
  • If Object:
    • Requires a drawRegistry entry.
    • Calls entry.init() immediately.
    • Stores { type: "object", drawRegistry: entry, dirty:false, parameters: entry.params }.
    • Calls drawActiveTab().

High-leverage topic: Object tab identity is based on item.name. That means duplicate names collide (same tabId). Your file comment says “Always open a NEW tab (no dedupe),” but the tabId scheme can still collide. This is a conceptual mismatch worth discussing.

3.3 deleteTab(tabId)

  • Removes the DOM button.
  • Deletes the tab state from uiState.draw.tabs.
  • Activates a neighbor tab if possible; otherwise rebuilds subtabs.

4) drawActiveTab(): The Central Execution Pipeline for Draw

This is the main “why things happen” function in Draw.

Sequence (as implemented):

  1. Identify tabId and confirm it is an object tab.
  2. Build the caption bar for the entry (help/menu/script path).
  3. Prepare #sketchpad and attach the shared canvas.
  4. Clear the canvas context deterministically.
  5. Prepare the interaction overlay layer (size/position/pointer-events).
  6. Build parameter controls into #action (by calling buildParameterControls(state,...)).
  7. Sync params and call entry.update(params) then entry.draw().

4.1 ParameterControls coupling points

Draw wires two behavioral callbacks onto the per-tab state:

  • state.redrawHandler = drawActiveTab (the control UI can trigger redraw)
  • state.onParamChange = () => markTabDirty(tabId) (param changes mark “dirty”)

What to discuss: This is the “bridge” between UI controls and drawing. It is where UI events become “redraw the object.” If something redraw-related is wrong, this is the chokepoint.

4.2 Overlay alignment: why Draw cares

  • Draw assumes canvas overlays live inside #sketchpad and coordinate space is local.
  • Draw explicitly sizes and positions the “interaction” layer to match the canvas.
  • Point-picker dots will later re-enable pointer events on specific nodes; the base layer is set to pointerEvents:none.

Key topic: Canvas overlay ownership and alignment is a frequent source of “it draws but I cannot interact” bugs. The position/width/height assumptions here must match overlay.js’s actual structure.

5) Caption Bar + Menu: setDrawCaption() and buildDrawMenuItems()

5.1 setDrawCaption(entry)

  • Title is entry.name.
  • No Prev/Next.
  • Menu is built dynamically when opened.
  • It finds the registryKey by searching window.drawRegistry for the entry object reference.
  • Script path is constructed as: /drawRegistry/<registryKey>.js.

High-leverage topic: The “reverse lookup” (entry object → registry key) only works if the object stored in uiState is the exact same object reference that exists in window.drawRegistry. If you ever clone entries or create per-tab instances, this logic breaks and must be redesigned.

5.2 buildDrawMenuItems()

  • Help item via menuManager.buildHelpItem(tabName, itemName).
  • Show Script via showScriptOffcanvas(scriptPath, itemName).
  • Duplicate via copyActiveDrawObject().
  • Reset via resetActiveDrawObject().

6) Categories Rendering: collectRegistryEntries → groupEntriesByCategory → renderCategories

When Categories subtab is active, Draw renders category frames into #text.

Pipeline:

  • collectRegistryEntries() builds a flat list from window.drawRegistry.
  • groupEntriesByCategory() builds a sorted map by category.
  • renderDrawCategories() turns that into a categories.js descriptor and calls renderCategories("text", ...).
  • Clicking an item opens an object tab via addDrawSubtab({ name, entry }).

What to discuss: This is a pure “descriptor → categories.js rendering” flow, consistent with your architectural rule that categories.js should not know anything about manifests or tabs.

7) Dirty Tracking: markTabDirty() / markTabClean()

  • Dirty state lives per object tab: uiState.draw.tabs[tabId].dirty.
  • Dirty is reflected visually by adding “ *” to the tab label.
  • Parameter changes mark dirty via the callback installed in drawActiveTab().

Discussion point: What exactly counts as “dirty”? Only param changes? What about point dragging? What about duplicate/reset? The dirty mechanism should match your intended meaning.

8) Launch Intent: Home → Draw (consume-and-clear)

Draw contains a launch-intent consumption mechanism:

  • uiState.launch.pending signals that a cross-tab intent exists.
  • Draw consumes only if targetTab === "draw".
  • It “consume-and-clear” resets launch fields immediately.
  • If sourceType === "drawRegistry", it opens a new object tab for the referenced registryKey.

Critical to discuss: Your file currently has two launch mechanisms: consumeLaunchIfForDraw() and consumePendingLaunchIntoDraw(). The second one calls resolveDrawRegistryKeyOrId() and then calls showDrawWorkspaceFromState(), which is not defined in this file and appears to be a leftover from a different shape of Draw state. This is exactly the kind of “stray mechanism” that creates confusion and bugs.

9) Save/Restore: What Draw Can Actually Persist

saveDrawState() tries to serialize a snapshot of open tabs:

  • It builds shallowTabs keyed by tabId.
  • For object tabs, it attempts to map the entry object back to a registry key.
  • It stores:
    • type, dirty
    • parameters via structuredClone
    • drawRegistry as the registry key string

Key discussion point: This “saved state” is not currently used by restoreDrawTab() to rebuild tabs, because restoreDrawTab() instead uses the live uiState.draw.tabs objects. If you want real persistence across full reloads, you will eventually need a restore path that rebuilds object tabs from saved keys + saved params, re-calling entry.init(), applying params, then drawing.

10) The One Sentence That Summarizes draw.js

draw.js is an internal subtab system that wraps drawRegistry entries as live object instances, keeps per-tab params + dirty state in uiState.draw.tabs, and renders the active entry by building caption/menu + parameter controls, syncing overlays, and calling entry.update() then entry.draw() against the shared canvas.
