How Sketchpad Manifest Data Is Read, Stored, and Used

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on two files:

  • ui/manifest.js (the generic loader and cache)
  • ui/patterns.js (one consumer of manifest data)
Scope of this treatise
1) Exactly how manifest.json data is loaded and cached by ManifestManager.
2) Exactly how patterns.js receives and uses that manifest data.
3) How a tab knows to “rewrite/refresh” manifests after they are updated, and what the refresh sequence is.

1. What “manifest” means in this architecture

A “manifest” is JSON data that describes the available items in a content area. In this architecture there are two possible directory models, and ManifestManager.get(basedir) automatically selects between them:

1.1 DirectoryRegistry model (categories)

If ../<basedir>/directoryRegistry.json exists:

  • That registry file is read as an array of category names.
  • For each category, ../<basedir>/<category>/manifest.json is loaded (if it exists).
  • The returned result is an “array-of-arrays”, where each inner array corresponds to one category.
[
  [ /* category 0 items */ ],
  [ /* category 1 items */ ],
  ...
]

1.2 Flat manifest model (no categories)

If no directory registry exists but ../<basedir>/manifest.json exists:

  • That single file is loaded as a flat array.
  • The returned result is that array.
[
  { /* item */ },
  { /* item */ },
  ...
]

1.3 Nothing exists

If neither model exists, get(basedir) returns [].

2. manifest.js: reading and caching rules

ui/manifest.js defines ManifestManager, then exports a singleton instance named manifest. Tabs import manifest and call manifest.get(...).

2.1 The only official cache is ManifestManager.cache

In the class constructor: 

this.cache = {};         // basedir → loaded data (array or array-of-arrays)
this.registryCache = {}; // basedir → directoryRegistry array (if present)

The meaning is:

  • cache[basedir] stores the result of a successful load for that basedir.
  • registryCache[basedir] stores the directory registry array if the directoryRegistry model was used.

Important: The cache is keyed only by basedir. So manifest.get("patterns") and manifest.get("gallery/Ideabook") are cached independently.

2.2 get(basedir) load algorithm (exact sequence)

  1. If this.cache already contains basedir, return it immediately.
  2. Else check for directoryRegistry.json.
  3. If present: load it, validate it is an array, then for each category:
    • Check if the category’s manifest.json exists.
    • If it exists: load it, validate it is an array, push it.
    • If it does not exist: push an empty array for that category.
    Cache and return the resulting array-of-arrays, and cache the directory registry array.
  4. If no directory registry: check for the flat manifest.json.
  5. If present: load it, validate it is an array, cache it, return it.
  6. If nothing exists: cache [], return [].
Fail-fast behavior in manifest.js
If a directory registry exists but is not an array, it throws.
If a category manifest exists but is not an array, it throws.
If a flat manifest exists but is not an array, it throws.

2.3 getRegistry(basedir)

getRegistry is a convenience getter for the directory registry, but it only works if:

  • A directoryRegistry existed, and
  • get(basedir) has already been called at least once (so the registry is cached).

If either condition is false, getRegistry(basedir) returns [].

2.4 clearCache()

clearCache() resets both caches: 

this.cache = {};
this.registryCache = {};

Meaning: after clearCache, any subsequent manifest.get(basedir) will reload from disk (through fileLayer).

3. patterns.js: how it receives manifest information

In the Patterns tab, manifest data is loaded once, reshaped once, then used thereafter. Patterns does not repeatedly call manifest.get("patterns") directly in every operation. Instead it builds and uses a tab-friendly structure stored at manifest.cache.patterns.

Structural note (Patterns adds an additional cache)
ManifestManager already has its own cache at manifest.cache (class field).
Patterns creates a second, separate cache object by writing manifest.cache.patterns.
That is not part of ManifestManager’s class contract; it is an application-level convention.

3.1 ensurePatternsManifestLoaded(): one-time load + reshape

Patterns uses a dedicated loader: 

async function ensurePatternsManifestLoaded() {
  if (manifest.cache && manifest.cache.patterns) return;

  const raw      = await manifest.get("patterns");
  const registry = manifest.getRegistry("patterns");

  ...build map...
  manifest.cache.patterns = map;
}

Interpretation:

  • It checks whether manifest.cache.patterns exists. If yes, it does nothing.
  • Otherwise it calls manifest.get("patterns"), which returns an array-of-arrays.
  • It calls manifest.getRegistry("patterns") to get the category names.
  • Then it reshapes the array-of-arrays into a map keyed by category name.
{
  "curve_stitch": [ entry, entry, ... ],
  "polygons":     [ entry, entry, ... ],
  ...
}

This reshape is the crucial bridge between the generic loader output and the Patterns tab’s usage model. Everything else in Patterns assumes it can do: 

manifest.cache.patterns[categoryName]  // → list of entries

3.2 Where Patterns uses the manifest cache

Patterns uses manifest.cache.patterns in three main areas:

3.2.1 Category list view

When showing categories (showCategoryList()):

  • It calls ensurePatternsManifestLoaded().
  • It reads const groups = manifest.cache.patterns;.
  • It passes that map to buildCategoryDescriptor(...), which drives renderCategories(...).

The category frames are built purely from the cached manifest map, not by scanning the filesystem or re-reading JSON at render time.

3.2.2 Pattern selection and display

When a pattern is selected, showSelectedPattern(category, index) does:

  • Calls ensurePatternsManifestLoaded().
  • Looks up the list for the category:
    const list = manifest.cache.patterns?.[category] || [];
  • Selects the item by index: const item = list[index];
  • Builds the script path and helpKey from the category + filename.

So the manifest entry supplies:

  • item.filename (used to load the module and to build image/thumb paths)
  • item.title (used for caption display, fallback label rules, etc.)
  • Any other manifest fields you may add later (tags, description, etc.)

3.2.3 Thumbnail grid

When rendering the thumbnail grid in renderPatternThumbGrid(category):

  • It reads const list = manifest.cache.patterns[category];
  • It passes that list into renderThumbnailGrid(...).
  • The thumbnail path uses entry.filename:
    ./patterns/<category>/images/thumb_<filename>.png

Again: no filesystem work happens here; the manifest is the authoritative list.

4. What “stored” means: three layers of storage

There are three distinct places where manifest data exists:

  1. On disk: JSON files under /patterns (and other basedirs).
  2. In ManifestManager: manifest.cache[basedir] and manifest.registryCache[basedir].
  3. In Patterns’ reshaped cache: manifest.cache.patterns (categoryName → list).

So “read, stored, and used” maps to:

  • Read = fileLayer loads JSON from disk (called by ManifestManager.get).
  • Stored = cached into ManifestManager + reshaped into Patterns’ map cache.
  • Used = UI/controller logic reads the map cache for categories, thumbnails, captions, and script lookup.

5. How a tab knows manifests were updated (refresh / rebuild lifecycle)

There are two “update” situations:

  • Rebuild/maintenance: Node scans folders and rewrites manifests on disk.
  • Edit: Node edits a single manifest entry (e.g., title change), rewriting JSON on disk.

In both cases, the key is:

The browser cannot detect on-disk changes automatically.
The tab must explicitly decide “my cached data is stale”, then clear caches and reload.

5.1 Patterns’ explicit refresh path (Rebuild & Validate command)

In wirePatternsCommandsButton(), when “Rebuild & Validate” is clicked:

  1. UI calls nodeRebuildAndValidateManifests() (browser → nodeLayer → Node service).
  2. Node performs maintenance and returns a report.
  3. Patterns invalidates caches:
manifest.clearCache();
if (manifest.cache) delete manifest.cache.patterns;

Then Patterns reloads: 

await ensurePatternsManifestLoaded();

Then Patterns re-renders whichever view is active:

  • If view is “pattern”: call showSelectedPattern(cat, idx).
  • Else: call showCategoryList().

So “knowing manifests changed” is not automatic: the command handler knows it just asked Node to rewrite manifests, therefore it clears caches and reloads.

5.2 Edit operations: same refresh requirement

“Edit Manifest Title” (or any manifest-editing command) should follow the same pattern after Node confirms the write:

  1. Browser triggers a Node task that writes updated JSON.
  2. Tab invalidates relevant caches.
  3. Tab reloads manifest data.
  4. Tab refreshes any UI derived from that manifest data (caption, category list labels, ordering if affected, etc.).

6. Patterns’ dependency boundary: what Patterns assumes ManifestManager provides

Patterns relies on exactly these ManifestManager features:

  • await manifest.get("patterns") loads raw data (array-of-arrays for directoryRegistry model).
  • manifest.getRegistry("patterns") returns category names (after get has been called).
  • manifest.clearCache() can be used after Node writes to disk.

Everything else is a Patterns tab convention:

  • Building manifest.cache.patterns as a categoryName → list map.
  • Using that map as the single data source for category frames and thumbnails.

7. Concrete end-to-end example (manifest → UI → script execution)

  1. Patterns init calls ensurePatternsManifestLoaded().
  2. manifest.get("patterns") reads:
    • patterns/directoryRegistry.json
    • and for each category: patterns/<category>/manifest.json
  3. ensurePatternsManifestLoaded reshapes into:
    manifest.cache.patterns = { categoryName: [entries...] }
  4. showCategoryList() builds clickable category frames from that map.
  5. User click stores selection into uiState.patterns and calls showSelectedPattern(category, idx).
  6. showSelectedPattern looks up the manifest entry to get filename and title.
  7. It builds scriptPath, loads the module, executes it into the canvas.
  8. It updates UI derived from the manifest entry (caption title and thumbnail grid).

8. Help-system integration notes

If your help system uses menuManager.buildHelpItem(tabName, helpKey), Patterns supplies:

  • tabName = "patterns"
  • helpKey = "<category>/<filename>"

For a pattern file patterns/curve_stitch/myParabola.js, the help key becomes: 

curve_stitch/myParabola

Depending on your convention, a typical help path would be: 

help/patterns/curve_stitch/myParabola.html

Note the parallel concept:

  • Content manifests describe Patterns/Gallery/etc items.
  • Help manifests describe which help pages exist.

9. Summary checklist

  • ManifestManager.get(basedir) loads directoryRegistry model (array-of-arrays) or flat model (array).
  • ManifestManager caches results per basedir, plus optional directory registry per basedir.
  • Patterns reshapes into manifest.cache.patterns as a category map.
  • Patterns consumes that map for category frames, thumbnails, and selecting items by index.
  • After Node rewrites manifests, the tab invalidates and reloads using:
    manifest.clearCache(); delete manifest.cache.patterns; await ensurePatternsManifestLoaded();

End of treatise.
