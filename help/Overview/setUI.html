setUI.js — Sketchpad Tab Orchestrator (TabSpec Architecture)

This page is intentionally “raw help HTML”: it is written as a single self-contained page so you can drop it into your help system as-is, and/or split it later into smaller pages. The discussion is based on one file:

  • ui/setUI.js
Scope of this treatise
1) What “tab orchestration” means in Sketchpad (and what setUI.js owns).
2) How TabSpec objects are registered and invoked (init vs restore).
3) The exact activation algorithm and where uiState is consulted.
4) What “theme” means and when it is applied.
5) How click events reach setUI(), and what happens on initial startup.
6) The “launch intent” mechanism: Home → Draw (or any tab jump) without cross-tab coupling.

1. What this file is responsible for (and what it refuses to do)

setUI.js is the top-level tab switchboard. Its job is to:

  • Know which TabSpec exists for each top-level tab
  • Decide whether a tab should cold-init or restore
  • Clear shared UI regions only on cold-init
  • Update tab-button highlighting
  • Apply per-tab theme classes
  • Wire the main tab bar click events
  • Run startup initialization once on DOMContentLoaded
  • Consume a “launch intent” that requests a follow-on tab jump
What setUI.js deliberately does NOT do
It does not render any tab content itself. It does not build category frames, grids, captions, controls, or overlays. It only delegates to TabSpec objects to do those things.

2. The TabSpec contract (how tabs plug in)

Sketchpad tabs are implemented as TabSpec objects. In this file they are imported and registered in one place: 

const TabRegistry = {
  home:      HomeTabSpec,
  draw:      DrawTabSpec,
  patterns:  PatternsTabSpec,
  gallery:   GalleryTabSpec,
  utilities: UtilityTabSpec,
  figures:   FiguresTabSpec
};

This registry is the authoritative “routing table” for tab switching. setUI.js assumes each registered TabSpec provides:

  • init(restoredFlag) (required)
  • restore() (required)
  • save() (optional, used elsewhere)
Important architectural rule enforced here
setUI.js only switches tabs and delegates. It does not try to be “smart” about each tab’s internal view model.

3. Startup model: START_APP means “Home cold init”

This file defines: 

const START = "START_APP";

That token is used only to represent the initial launch state. On startup, setUI.js treats START as:

  • Target tab is home
  • Always cold-init (not restore)

This is implemented in activateTab(): 

if (tab === START) {
  tabKey = "home";
  initTab(tabKey);
}

4. The two activation paths: init vs restore

The central role of setUI.js is deciding which of these two paths to use:

4.1 Cold init path

Cold init means: clear shared regions, then let the TabSpec build its UI. 

function initTab(tabKey) {
  clearDivs();     // clear shared regions
  spec.init(false);
}

clearDivs() is a shared utility that clears the common regions (caption/text/sketchpad/action/etc). The key point is: setUI.js owns that clearing step, so TabSpec.init can assume the region shell is empty on cold start.

4.2 Restore path

Restore means: do not clear anything here. The TabSpec restores its own UI based on uiState and cached manifests. 

function restoreTab(tabKey) {
  spec.restore();  // NO clearDivs here
}
Why restore does not clear
Restoring is meant to rebuild whatever view existed last (categories vs item vs grid), using uiState saved state. Clearing here would introduce cross-tab assumptions and race the restore logic. Therefore restore is delegated cleanly to the TabSpec.

5. The master decision logic: activateTab()

The exact “init vs restore” decision is here:

  1. If starting: force Home cold init
  2. Else if uiState[tabKey].saved exists: restore
  3. Else: cold init
  4. Then set uiState.activeTab and apply tab highlight
const saved = uiState[tabKey] && uiState[tabKey].saved;
if (saved) restoreTab(tabKey);
else initTab(tabKey);

uiState.activeTab = tabKey;
setActiveTab(tabKey);
Key meaning of uiState.<tab>.saved
It is the only signal used here to distinguish restore vs cold init. setUI.js does not use any other flags.

6. Tab button highlighting: cosmetic only

Sketchpad uses a Bootstrap-like tab bar. setUI.js does not rely on Bootstrap tab events; it applies the “active” class itself.

  • setActiveTab(tabKey) selects all #mainTabs .nav-link buttons
  • It maps each button’s id (like patterns-tab) to a tabKey
  • It adds active only to the selected one

This function is explicitly “cosmetic only”: it does not activate a tab, it only reflects the activation state in the UI.

7. Theme application: wrapper class switches per tab

Sketchpad uses theme classes on the top wrapper element: 

theme-home
theme-draw
theme-patterns
theme-gallery
theme-figures
theme-utilities

applyTheme(tabKey) does two things:

  1. Remove any existing theme class from #wrapper
  2. Add the theme class for the activated tab
Order matters
Themes are applied before init/restore is called. This ensures any DOM a tab creates will inherit the correct theme styling immediately.

8. setUI(tab): the public entry point

setUI() is the one public function exported by this file. All top-level tab switches go through it.

Its responsibilities are:

  1. Validate the tab name (except START)
  2. Apply the correct theme first
  3. Activate the tab (init or restore)
  4. Consume a pending “launch intent” and perform a follow-on tab jump

8.1 Input validation

For non-START tabs, it requires the tab exists in TabRegistry: 

if (tabName !== START && !TabRegistry[tabName]) {
  throw new Error("setUI: unknown tab " + tabName);
}

This prevents silent routing bugs when a tab key is misspelled.

8.2 Activation

Activation is delegated to activateTab(). setUI.js does not mix the two responsibilities.

9. The “launch intent” mechanism (decoupled tab jumps)

After activation, setUI.js checks for: 

uiState.launch.pending === true

If present, it reads: 

uiState.launch.targetTab

Then it clears pending FIRST (critical) and calls setUI(targetTab) unless it is already active.

What launch intent is for
It allows one tab (commonly Home) to request “go to another tab” without directly calling into that tab’s controller. This keeps cross-tab coupling out of tab modules.
Why pending is cleared before recursion
If pending were not cleared first, calling setUI(targetTab) would re-enter this block and could cause loops or repeated jumps. The code clears the intent before the recursive setUI call.

10. Event wiring: main tab buttons → setUI()

Tab switching from user clicks is wired in onDomContentLoaded():

  1. Initialize menu manager
  2. Initialize overlay manager
  3. Attach click handlers to each main tab button
  4. Call setUI(START) once
window.addEventListener("DOMContentLoaded", onDomContentLoaded);

Each click handler calls: 

handleTabChange(btn.id) → mapTabIdToKey(tabId) → setUI(tabKey)
Mapping exists because button ids are HTML-centric
The UI uses ids like "patterns-tab". The registry uses keys like "patterns". mapTabIdToKey() bridges those two vocabularies.

11. Quick reference: what each function “means”

  • TabRegistry — the authoritative list of top-level tabs.
  • setActiveTab(tabKey) — cosmetic highlight only (active class).
  • mapTabIdToKey(tabId) — HTML id → registry key translator.
  • applyTheme(tabKey) — swap wrapper theme class before rendering.
  • restoreTab(tabKey) — delegate only; no clearing.
  • initTab(tabKey) — clear shared regions; then TabSpec.init(false).
  • activateTab(tabKey) — decide restore vs init using uiState.<tab>.saved.
  • setUI(tabKey) — public entry; theme + activation + launch-intent consumption.
  • handleTabChange(...) — click event wrapper that calls setUI().
  • onDomContentLoaded() — one-time initialization and first activation.

12. Summary checklist

  • One routing table: TabRegistry defines all top-level tabs.
  • One public entry: setUI() is the only supported way to switch tabs.
  • One restore signal: uiState.<tab>.saved decides restore vs cold init.
  • Clearing happens only on cold init via clearDivs().
  • Theme is applied first, before init/restore builds DOM.
  • Launch intent enables cross-tab jumps without direct coupling.

End of treatise.
