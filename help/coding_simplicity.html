Coding Simplicity

This document describes a philosophy of simplicity for code written in Sketchpad, derived from working sessions between Barry and Claude. It exists because Claude's trained instincts tend toward complexity — frameworks, derived quantities, general machinery — and this document is intended to be read at the start of a session to orient Claude toward a simpler way of working.

The core principle is: code should reflect the idea directly, not the machinery needed to produce the output.

Part 1 — The Central Pattern

Almost every simplification in practice comes down to one distinction:

  • Claude's instinct: compute a value from a formula.
  • Barry's instinct: start at a point and increment.

When seeding points on a grid, Claude reaches for: 

x = xLeft + (xRight - xLeft) * i / (M - 1)

Barry replaces this with: 

for (let x = x0; pts.length < M; x += dx) pts.push(x);

The formula computes each position independently from derived bounds. The increment just adds a delta to the previous value. The increment version is shorter, more readable, and makes the structure of the thing visible at a glance. It also makes parameters obvious: the only things that matter are the starting point and the delta — not a left bound, a right bound, and a count all held together.

Rule: When building a sequence of evenly spaced values, always choose increment-from-start over formula-from-bounds. The starting point and the delta are the natural parameters. Everything else is derived and should not appear in the code.

Part 2 — Don't Build the General Machinery

Claude's instinct when faced with a pattern is to build the general case first. Barry's instinct is to name the actual patterns directly.

Example: Sliding window vs. named triplet types

When building parabola triplets from a grid of points, Claude's approach was to build an intermediate sequence array and slide a window of 3 across it: 

const seq = [];
for (let j = 0; j < M; j++) {
  seq.push(pt(extRow, j));
  if (j < M - 1) seq.push(pt(bandRow, j));
}
for (let k = 0; k < seq.length - 2; k++)
  triplets.push([seq[k], seq[k+1], seq[k+2]]);

Barry recognized that the sliding window only ever produces two shapes:

  • Type A: [ext[j], band[j], ext[j+1]] — apex on band row
  • Type B: [band[j], ext[j+1], band[j+1]] — apex on exterior row

The simpler version names these directly: 

/* Type A: apex on band row */
for (let j = 0; j < M - 1; j++)
  triplets.push([pt(extRow, j), pt(bandRow, j), pt(extRow, j+1)]);

/* Type B: apex on exterior row */
for (let j = 0; j < M - 2; j++)
  triplets.push([pt(bandRow, j), pt(extRow, j+1), pt(bandRow, j+1)]);

No intermediate array. No window. The geometry is visible in the code.

Rule: Before building general machinery (sequences, windows, indices), ask: what are the actual things being produced? Name them directly. The general machinery is often hiding two or three simple cases that can be stated plainly.

Part 3 — Don't Compute What You Can Choose

A related instinct in Claude is to derive parameters from other parameters. Barry's approach is to choose the primitive directly and let everything else follow.

Example: Grid layout

When seeding a grid of points, Claude computed the grid dimensions from radius, midpointX, and midpointY: 

const xLeft  = cx - r / 2;
const xRight = cx + r / 2;
const topX = Array.from({ length: M }, (_, i) =>
  xLeft + (xRight - xLeft) * i / (M - 1)
);

Barry replaced this with: choose a top-left corner and a delta. 

const x0 = 100, y0 = 50;
const dx = params.width * params.scale;
const dy = params.height * params.scale;

Everything else falls out from these four values. There is no derived left bound, right bound, or center. The consequence is that adding width, height, and scale controls is a trivial change — you just expose the primitives that were already there. In the original version, it would have required rethinking the entire coordinate derivation.

Rule: Expose primitives, not derived quantities. If a parameter is computed from two others, ask whether those two others are the more natural controls. Parameters should be the things you actually want to adjust, not the things the formula needs.

Part 4 — Don't Create Points You Don't Use

Claude's first grid implementation stored a full (2N-1) × (2M-1) rectangular grid — every intersection of exterior and band rows and columns. Only half of those points were ever referenced in the parabola triplets. The other half appeared as ghost drag handles with no geometry attached.

The fix was to recognize that exterior rows and band rows have different x sequences:

  • Exterior rows: x0, x0+dx, x0+2dx, ... (M values)
  • Band rows: x0+dx/2, x0+3dx/2, ... (M-1 values, the midpoints)

Once that structure was explicit, _seed became: 

for (let i = 0, y = y0; i < 2*N-1; i++, y += dy) {
  const xs = (i % 2 === 0) ? extX : bandX;
  xs.forEach(x => params.points.push({ x, y }));
}

Every point stored is a point used. No orphans.

Rule: Only create what is needed. If points, intermediate arrays, or objects are created but not all used, that is a sign the structure does not match the actual geometry. Find the structure that matches, and the unused elements disappear.

Part 5 — The Working Method

The simplifications above do not happen automatically. They require a particular way of working together.

Think before writing

Claude should describe its intended approach before writing any code. Barry will often stop it here and redirect toward the simpler version. This is more efficient than writing code and then simplifying it.

Ask: what is it really?

When Claude proposes a structure, Barry often responds with "not quite" and restates the thing more directly. The correct response to this is not to add another layer of abstraction — it is to ask: what is the actual thing being described? Usually the answer is smaller and more direct than what Claude proposed.

Small steps, verified

Each change is small and verified before the next one is made. This is not just about coding comfort — it preserves architectural ownership. When each step is understood before the next begins, the person writing the code understands every line of it.

Eliminate, don't guard

When a block of code is wrong, remove it entirely. Do not add a conditional guard around it. Guarded-but-wrong code accumulates and obscures the structure.

Rule: The goal is code where the idea is visible. If you have to explain why a block of code is there, the code is probably not simple enough yet.

Part 6 — Before/After Reference

The following pairs show Claude's instinct alongside the simpler replacement. When Claude notices it is about to write something in the left column, it should stop and find the right column version instead.

Claude's instinct Simpler replacement
Compute position from formula using derived bounds Start at a point, increment by delta
Build intermediate sequence array, slide window of 3 Name the two triplet types, push directly
Store full rectangular grid of all intersections Store only the points that are actually used
Expose radius, midpointX, midpointY as controls Expose width, height, scale — the actual primitives
Add a conditional guard around wrong code Remove the wrong code entirely
Build the general case first Name the actual cases that exist and state them plainly
Write code, then simplify Describe approach first, think before writing

Summary

Simplicity in this codebase is not a style preference — it is a structural property. Code that reflects the idea directly is easier to change, easier to debug, and easier to extend. The joinedParabs example demonstrates this concretely: adding width, height, and scale controls to the final version was a three-line change because the primitives were already explicit. The same change to the original version would have required rethinking the entire coordinate system.

The discipline required is: stop before building, ask what the thing really is, and find the version where the answer is visible in the code.
