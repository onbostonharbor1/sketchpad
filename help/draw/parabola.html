parabola.js — Analysis

drawRegistry entry · id: "parabola" · version: 2.0 · category: fundamental

A production-ready drawRegistry primitive that renders a stitched parabola — a classic string-art construction where evenly-spaced points along two line segments are connected by straight lines, creating the visual illusion of a parabolic curve. The entry is fully interactive: six drag handles on the canvas allow real-time reshaping of both arm lines.

points[] layout: indices 0–2 correspond to line 1 (start, end, midpoint); indices 3–5 correspond to line 2. The midpoint handles (2 and 5) are derived — they are not independent geometry; they move the entire line when dragged.

init()

Called once when the drawing is first loaded or reset. Three responsibilities:

  1. Clear handles: p.points.length = 0 drops old handle objects so stale references can't leak across reload cycles.
  2. Build master geometry: constructs Line and StringThing instances from current params, stored in this.elements.
  3. Populate handles: pushes six { x, y } objects into p.points. The midpoints at index 2 and 5 are computed from l.midpoint().
const m1 = l1.midpoint();
p.points.push({ x: p.line1_pt1.x, y: p.line1_pt1.y }); // [0] start
p.points.push({ x: p.line1_pt2.x, y: p.line1_pt2.y }); // [1] end
p.points.push({ x: m1.x, y: m1.y });                   // [2] midpoint (derived)
Storing geometry in this.elements rather than rebuilding it on every draw() call means the Line objects persist across frames — important because update() calls mutating methods on them directly.

update(incoming)

Handles two entirely different kinds of change in a single method, dispatched on whether incoming.points is present.

Branch 1 — Interactive drags (incoming.points truthy)

The interactor mutates the points[] array directly before calling update(). The method must decide which handle was moved and reconcile the Line object. It applies midpoint-first priority: 

const incomingMid1 = new Point(p.points[2].x, p.points[2].y);
if (!incomingMid1.isSame(l1.midpoint())) {
    l1.moveMidpointTo(incomingMid1);   // translate whole line
} else {
    l1.setStart(new Point(p.points[0].x, p.points[0].y));
    l1.setEnd  (new Point(p.points[1].x, p.points[1].y));
}

Because all three handles (start, end, midpoint) are draggable simultaneously, the check disambiguates intent: if the midpoint moved, it was a translation drag — the endpoints are recalculated by the Line. If the midpoint is unchanged, an endpoint was dragged and the line is reshaped.

After resolving geometry, a double sync is performed:

  • p.line1_pt1 = { x: s1.x, y: s1.y } — keeps serializable params current.
  • p.points[0].x = s1.x; p.points[0].y = s1.y — keeps visual handles accurate after a midpoint-driven translation.
In-place mutation is mandatory. The interactor holds direct object references into p.points[]. Replacing array slots with new objects (p.points[0] = { x, y }) would break those references — the interactor would render its handles at stale positions. Always mutate .x / .y on the existing objects.

Branch 2 — Slider and style changes

for (const [key, val] of Object.entries(incoming)) {
    if (key === "lineWidth") { thing.lineWidth = p.lineWidth = Number(val); }
    else if (key === "shorten")  { thing.shorten  = p.shorten  = Number(val); }
    else if (key === "truncate") { thing.truncate = p.truncate = Number(val); }
    else if (key in thing)       { thing[key] = p[key] = val; }
}

A generic loop avoids a long if/else chain for color and other future style params. Numeric coercion (Number(val)) is applied explicitly to the three slider-driven properties since widget values arrive as strings.

draw()

draw() {
    const { l1, l2, thing } = this.elements;
    drawAParab(thing, l1, l2);
}

Intentionally minimal. All logic lives in init and update; draw() is a pure delegation. This means it can be called repeatedly (e.g., on every animation frame or slider change) without side effects.

The Overlay / Interaction Layer

parabola.js declares overlays: [] — it does not use the DOM overlay system. Instead, interactivity comes from a dedicated canvas layer managed by interactor.js.

How armInteractor works

StepWhat happens
1. armInteractor(instance) calledDisarms any previous interactor, then reads instance.params.points.
2. activatePointPicker(points, config)Sizes the "interaction" canvas to match window.drawCanvas, makes it visible and pointer-events-active.
3. Initial renderDraws six red dots (LEGO Bright Red) with white stroke over the canvas at the handle positions.
4. Mouse events (window-scoped)mousedown finds the nearest handle within hitTolerance: 10px. mousemove mutates points[draggedIndex].x/y and calls onUpdate(). mouseup releases the drag.
5. onUpdate()Calls instance.update(instance.params), then triggers a redraw via instance.redrawHandler or the active tab's handler.
6. disarmInteractor()Aborts the AbortController (removes all three listeners), clears the interaction canvas, hides it.

Signal-guarded render

function render() {
    if (signal.aborted) return;  // ghost-draw guard
    ctx.clearRect(0, 0, canvas.width, canvas.height);
    // ...draw handles...
}

Without this guard, a slider change arriving after disarmInteractor() could invoke a queued render() call that repaints handles on a canvas that is supposed to be empty. The abort check prevents that.

One Architectural Note

params.points serves dual duty: it is both the interactor's shared mutable state and a serializable param field. If this entry is ever serialized to JSON and restored, points[] should be re-derived from the four line*_pt* params (as init() already does) rather than restoring the saved points[] directly. Restoring raw handle positions would bypass the midpoint-derivation step and could leave the six handles inconsistent with the actual line geometry.
